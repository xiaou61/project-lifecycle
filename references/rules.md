# 分层规范与恢复协议

使用本参考处理“项目有哪些固定规范”“上下文压缩后继续”“这个任务是否可以例外”等问题。它把不会变的 Skill 底线、当前项目的常驻规则和一次工作项的特殊约束分开，避免把临时要求写成永久规则。

## 三个范围

### Skill 全局底线

这是所有使用本 Skill 的项目、所有受管理工作都必须遵守的最低合同，写在 `SKILL.md`：

- 默认用中文沟通和创建项目工件；代码标识符、路径、命令和机器状态保留原样。
- 开始或恢复重要工作前，从工件重新判断项目根目录、工作项、阶段、状态和下一步。
- Agent 不自行批准需求、方案、设计或任务计划；“继续”本身不是批准。
- 实质性范围、行为、接口、数据、安全或架构变化必须停下并回到最早受影响的工件。
- 不覆盖用户已有资料，不把建议或未运行的检查写成事实，不凭空声称测试通过。
- 代码、可执行测试和项目资料各归其位；完成后只沉淀有证据且能影响未来工作的知识。
- 小改动按风险走短路径，不因为 Skill 被发现就强迫创建完整工作项。

这些底线不能被项目文件或工作项文档静默放宽。需要改变 Skill 行为时，应修改 Skill 版本，而不是在项目里偷偷添加例外。

### 项目常驻规范

目标项目的 `.agent/rules/always.md` 适用于该项目的每一个任务。它只放该仓库长期有效的事实和约束，例如：

- 必须使用的语言、框架、运行时和包管理器。
- 源码、生成文件、数据库迁移和测试的真实位置。
- 必须运行的格式化、静态检查、单元测试和集成测试命令。
- API、兼容性、安全、隐私、日志、部署或提交方面的项目约束。
- 哪些目录只允许工具生成，哪些文件禁止手工编辑。

初始化器只写入一份可安全开始工作的最小模板，不会猜测项目命令。维护者应把“待项目确认”的事实补全，并将 frontmatter 的 `configured` 改为 `true`；规则未确认前，Agent 不应把未知命令当成已完成检查。

### 工作项约束

当前工作项的 `.agent/changes/<WORK编号>-<中文名称>/requirements.md` 记录本次变更的目标、非目标、验收标准和特殊约束。提案、设计和任务可以进一步明确实现边界，但只能在已批准范围内收敛，不能偷偷扩大范围。

工作项约束可以比项目常驻规范更严格，也可以选择项目允许的已知方案；不能静默取消项目常驻规范。若确实需要例外，先在 `always.md` 的例外记录中写明范围、理由、批准人、起止日期和验证方式，再继续当前工作。

## 优先级与冲突

先遵守平台、系统和开发者指令，再遵守用户当前明确的目标与授权；本 Skill 的全局底线、项目入口规则和项目常驻规范共同约束实现。项目文件之间按以下顺序处理：

```text
AGENTS.override.md
  > AGENTS.md
  > .agent/rules/always.md
  > 当前工作项 requirements.md 的约束
  > proposal.md / design.md / tasks.md 的实现细节
```

这里的“更高”不代表可以违反平台安全或用户授权，也不代表更具体的文档能自动推翻更高层规则。发现冲突、缺少批准或规则无法判断时，先停下来报告冲突和受影响范围；不要自行选择一个方便实现的解释。

## 上下文压缩、换会话与跨对话接力

完整的恢复顺序、`WORK-*` 接力提示词、阶段门槛、标准状态块和自然语言触发方式统一维护在 [references/workflow.md](workflow.md)。本文件只定义规范分层、优先级和例外边界，避免同一套执行步骤在多个参考文件中漂移。

上下文被压缩、会话切换或用户只说“继续”时，必须按 `workflow.md` 重新读取入口规则、`.agent/rules/always.md`、状态查询、工作项需求和当前阶段工件；不能把上一轮聊天中的阶段、批准或项目事实当作当前事实。

## 写规范的判断

只有会影响多个未来工作项的稳定事实才进入 `always.md`。一次功能的取舍放在该工作项；一次失败的临时排查放在任务或验证报告；跨变更的决策理由放在 `.agent/notes/`；共享协议和外部资料放在 `.agent/references/`；长期可检索知识放在 `.agent/memory.md`。如果一条规则只影响当前任务，不要提升为项目常驻规范。
