# 自然语言执行与跨对话接力协议

本文件是受管理工作项的标准执行协议。它回答三个问题：用户的一句话如何触发流程、Agent 每轮具体执行什么、换一个对话后如何只凭 `WORK-*` 恢复工作。需求、方案、设计、任务和测试的具体写法仍由各阶段参考文件负责。

## 核心约定

- 用户说自然语言即可，不要求背诵命令或文件名。
- `WORK-*` 是工作项的稳定身份和跨对话定位键，不是直接写代码的命令，也不代表批准任何阶段。
- `.agent/` 中的工件是事实源；聊天记录、文件时间戳和 Agent 的记忆都不能代替工件状态。
- 新对话、上下文压缩或用户说“继续”时，必须先恢复规范和状态，再执行当前阶段允许的动作。
- 用户明确批准某个工件后才能跨过对应门槛；Agent 不能自行批准，也不能把“继续”或“执行 `WORK-*`”解释成豁免门槛。

## 用户如何触发

只识别意图，不匹配固定口令：

| 用户表达 | Agent 当前动作 | 持久结果 |
| --- | --- | --- |
| “我有个想法”“想加一个功能” | 讨论结果、范围、约束和验收标准 | 讨论稳定后创建 `requirements.md` |
| “整理成需求”“这版需求确认” | 创建、修订或明确批准需求 | 已批准的 `requirements.md` |
| “给个方案”“需求确认了，继续” | 推荐方案并说明真实取舍 | `proposal.md` |
| “方案可以，做设计” | 批准方案并结合仓库完成详细设计 | `design.md` |
| “设计没问题，拆任务” | 批准设计并形成可执行计划 | `tasks.md` |
| “按计划开始做”“实施 WORK-003” | 先恢复状态；仅在任务计划已批准且没有阻塞时修改代码 | 源码、可执行测试和任务状态 |
| “测试一下”“验收 WORK-003” | 按验收标准执行真实检查 | `testing/plan.md` 和 `testing/report.md` |
| “当前状态”“查询 WORK-003” | 从工件重新推导阶段、任务、关系和下一步 | 默认不修改工件 |
| “继续” | 推进当前阶段已经获得授权的动作，或说明正在等待的确认 | 下一项被授权的结果 |

显式写 `$project-lifecycle` 总能请求使用本 Skill。目标项目的 `AGENTS.md` 已包含生命周期入口时，普通中文需求、`WORK-*` 编号或状态查询也应路由到本 Skill，不要求用户每次重复 `$project-lifecycle`。

## 每轮固定执行顺序

开始、恢复或查询受管理工作时，严格按以下顺序执行：

1. **确定项目**：确认目标项目根目录，读取适用的 `AGENTS.override.md`、`AGENTS.md` 和项目说明。
2. **恢复项目规范**：读取 `.agent/rules/always.md`。缺失、无效或有冲突时停止实现；`configured: false` 时可以继续讨论和设计，但实现前必须补全本次工作依赖的项目事实。
3. **查询真实状态**：从 Skill 安装目录运行：

   ```sh
   python -X utf8 scripts/project_status.py <project-root> --json
   ```

4. **定位工作项**：优先使用用户点名的 `WORK-*`，其次使用中文名称、内容匹配或唯一活动工作项；多个候选仍有歧义时只问一次。
5. **加载当前依据**：先读该工作项的 `requirements.md`，再根据当前阶段读取已经批准的上游工件、必要的 `.agent/specs/`、匹配的长期记忆和共享参考资料。
6. **检查能否行动**：核对阶段门槛、项目规范、硬依赖、软关联影响和工件内容是否一致。状态字段只用于定位，不能替代内容检查。
7. **执行一个明确动作**：继续讨论、创建当前阶段工件、修改代码、运行测试，或者在真实决策点停下等待用户确认。
8. **同步事实并汇报**：只按实际结果更新工件和任务状态，然后输出标准状态块与接力句。

`project_status.py` 的路径相对于已安装的 Skill，而不是目标项目的 `.agent/scripts/`。它是只读检查器，不维护第二份状态数据库。

## 阶段门槛

最早未满足的阶段决定下一步：

| 当前事实 | 当前阶段 | 允许的动作 |
| --- | --- | --- |
| `requirements.md` 不存在或为 `draft` | 需求讨论 | 继续澄清、修订并等待需求确认 |
| 需求已批准，提案不存在、为 `draft` 或 `stale` | 方案选择 | 创建或修订提案并等待确认 |
| 提案已批准，设计不存在、为 `draft` 或 `stale` | 详细设计 | 结合真实代码完成或修订设计 |
| 设计已批准，任务计划不存在、为 `draft` 或 `stale` | 实施计划 | 拆分任务并等待计划确认 |
| 任务计划已批准，存在未完成任务 | 开发实现 | 没有硬依赖和规范阻塞时修改代码并同步任务 |
| 实施任务全部完成，但没有通过的验证报告 | 测试验收 | 执行测试并记录证据、缺口和风险 |
| 上游工件一致、任务完成、验证通过 | 完成沉淀 | 核对稳定规格、长期记忆并可选归档 |

如果后期工件已经存在，但更早阶段缺失、未批准或失效，回到最早受影响阶段。用户可以明确合并或豁免某个门槛，但必须把该决定写入受影响工件；不能从催促语气或“直接做”中推断豁免。

## 跨对话接力

### 用户只需要记住什么

需求一旦获得稳定编号，新对话中只需要给出项目和 `WORK-*`。推荐提示词：

```text
$project-lifecycle 在当前项目继续 WORK-003，先恢复规范和状态，再按当前阶段执行。
```

如果要强调当前意图，可以说：

```text
$project-lifecycle 在当前项目继续实施 WORK-003。先恢复规范和状态；满足实施门槛就按已批准任务计划改代码并测试，否则告诉我还缺什么确认。
```

当新对话已经打开目标项目，并且根 `AGENTS.md` 已正确路由本 Skill 时，可以简写为：

```text
继续实施 WORK-003。
```

### Agent 收到后必须怎么做

1. 把 `WORK-003` 当作定位键，不把“实施”当作审批。
2. 完整执行“每轮固定执行顺序”，重新加载项目规则和当前工件。
3. 若任务计划已批准、受影响项目事实已配置、硬依赖已完成且没有漂移，直接进入代码实施，不要求用户重讲需求。
4. 若门槛未满足，停在最早缺失阶段，用一句话说明缺少的确认或阻塞，不跳过也不重新发明需求。
5. 若编号不存在，报告可用工作项或建议创建新工作项；不得凭编号臆造内容。

因此，跨对话接力的本质是“重新读取仓库事实后续办”，不是“把旧聊天搬到新聊天”。

## 标准状态与接力输出

每次实质性推进、状态查询或准备结束当前对话时，使用：

```text
当前：<中文工作项名称>（<WORK编号>）· <阶段> · <状态>
本次：<刚完成或正在处理的事情>
下一步：<Agent 将做什么，或等待用户确认什么>
接力：新对话可说“$project-lifecycle 继续 <WORK编号>，先恢复规范和状态，再按当前阶段执行。”
```

没有执行动作时可以省略“本次”。没有持久化 `WORK-*` 的早期讨论不输出“接力”。不要每轮复述完整流程、整份规范或所有工件；接力句必须使用真实编号，不能输出占位符。

## 工作项选择和多需求并行

按以下优先级选择工作项：

1. 用户明确点名的 `WORK-*`。
2. 用户明确点名的中文工作项名称。
3. 需求内容、受影响路径或验收标准能够唯一匹配的工作项。
4. 唯一未完成的活动工作项。
5. 仍有多个候选时，列出编号、中文名称和阶段，请用户选择一次。

不要按目录修改时间选择。Git checkout、解压和文件复制都会改变时间戳，却不代表用户意图。

硬依赖 `depends_on` 未完成时，可以继续澄清和设计，但不能进入实现或验收。软关联 `related_to` 不阻塞；跨阶段前检查共享接口、数据、模块和验收标准。两个需求不能独立批准和验收时应合并，而不是用循环依赖勉强连接。

## 自然语言批准

“这版需求确认”“方案就这么定”“设计没问题，按它拆任务”“任务计划确认，开始做”都可以构成有效批准，前提是明确指向当前工件，或由紧邻上下文唯一确定。

“继续”“往下做”“执行 `WORK-*`”只表达动作意图，不单独构成批准。用户可以在一句话中明确“批准并继续”；此时先记录批准，再执行下一项已授权动作。

## 现有项目与小改动

现有项目没有 `.agent/` 时，先读取项目规则和文档。用户明确要求用本 Skill 管理重要工作时，说明初始化只增加项目资料、不修改源码，然后运行初始化器；不要从 Git 反推并伪造过去的需求和设计。

单文件、低风险、边界清楚的小修复可以走短路径，不强制创建 `WORK-*`。新项目、重要功能、跨模块修改、公共行为或接口变化、迁移、安全和架构调整默认使用完整工作项。

不要创建 `.agent/current.md`、`state.json` 或手工索引。工作项身份和关系来自 `requirements.md`，阶段来自工件状态、任务状态和验证报告，查询器按需汇总。
