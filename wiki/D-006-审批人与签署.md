# D-006 · 审批签署由命令入口盖章，缺签署只警告不阻断

## 背景

需求是给生命周期工件加"审批人"：谁在什么时候批准了这份需求、方案、设计或任务，并且要能强制、要留签署痕迹。

现状是工件 frontmatter 只有 `status: draft | approved | stale` 三态翻转。批准动作在 `references/workflow.md` 的触发表里是纯口头的——用户说"这版需求确认"，Agent 把状态改成 `approved`，改完不留任何人和时间。

## 问题

阶段门槛（需求→方案→设计→任务）本来就有，缺的是**审计事实**。真正棘手的地方不是加字段，而是：

**Agent 能自己写 `approved_by`。** 如果签署只是"让模型往 frontmatter 里填一行名字和时间"，那么这份签署记录证明不了任何事情——模型完全可以在用户没说批准的情况下写上去，甚至编一个姓名。这比没有字段更糟，因为它看起来像证据。

第二个问题是**旧工件怎么办**。仓库里已有的工作项都没有签署字段，而 `item["warnings"]` 里的内容会在 `resume_context` 里变成阻塞项。如果把"缺签署"直接并进 warnings，所有历史工作项会在同一次升级后全部变成不可自动恢复——一次升级废掉全部历史。

## 备选方案

**方案 A：让 Agent 在批准时写入 `approved_by`/`approved_at`。**
被否掉：等于让模型替用户签字。字段存在但不可信，反而制造"看起来有证据"的假象。

**方案 B：真实签名（GPG / 证书 / 审批界面）。**
被否掉：这个 Skill 的签署人要证明的是"流程走过了"，不是密码学身份。为它引入密钥分发、验签和密钥丢失后的恢复流程，成本远超收益。同一台机器上的操作者本来就能伪造命令行调用，加签也只是把伪造成本抬高一点。

**方案 C：只由命令入口盖章，缺签署按兼容性警告报告。**
`project-lifecycle.ps1 approve` 是唯一写签署字段的入口：它把 `status` 置为 `approved`、写入 `approved_by`/`approved_at`/`approver_role`、并往 `updates.md` 追加一条 decision 记录，时间戳由脚本盖。缺签署时 `validate` 报警告、`validate --strict` 视为失败；时间戳格式错误一律是错误。

**方案 D：在方案 C 基础上，缺签署直接阻断恢复。**
被否掉：见上，会让所有历史工作项一次性失效。兼容期先按警告报告，旧工件按需补签。

## 决策与理由

采用**方案 C**。理由：

- **把签名动作从模型手里拿走**。时间戳来自脚本而不是模型的叙述，姓名必须由用户给出（`--by` 必填），并且这条记录同时落进追加式的 `updates.md`，和 frontmatter 用同一次执行盖同一个时间戳——两处对不上就说明有一处被手改了。
- **只签已经存在门槛的工件**。`requirements`、`proposal`、`design`、`tasks` 四个阶段工件，加验证报告的 `accepted_by`（业务验收，`testing.md` 早就写了 `passed` 不等于验收，这个缺口正好补上）。`lite` 短路径、`testing/plan.md` 不签；`.agent/specs/` 不签，因为稳定规格的改动本来就由工作项的需求和设计授权。
- **强制分级，而不是一刀切**。签署字段只能由入口写（防伪造）→ `--strict` 把缺签署视为失败（发布门）→ 门槛表规定"`status: approved` 但没有签署按未完成签署处理"（Agent 执行时遵守）。三层都不需要把旧项目变成不可用。
- **不新增身份名单文件**。`--by` 是必填自由文本。名单只防拼写错误和编造，对单人项目不值得再加一个文件和一套表格解析；真需要多人签字校验时再加（见下方重审条件）。

## 代价和后果

- **签署不是密码学证据**。它证明"这台机器上有人以某个姓名跑过 approve"，不证明那个人的身份。文档里不能把它说成"防篡改"。
- **旧工件要补签**。发布前 `validate --strict` 会因缺签署失败，这是一次性的迁移成本。
- **`approved_at` 是本地时间字符串**，带 numeric 时区（`2026-09-20 15:46:18 +0800`），不是 UTC。这样人读和 `updates.md` 一致，代价是跨时区比对要先归一化。
- **`approval` 是新增的 JSON 字段**，`schema_version` 保持 `2`：只新增字段不改旧字段，下游按字段读取不受影响。但 `validate` 的输出多了一类警告，集成方如果对警告数量做断言会受影响。

## 什么情况下该重审

- **多人协作需要身份校验时**：`--by` 的自由文本不够，那时才引入项目名单（校验姓名是否在册）甚至接 Git 提交签名。判断信号是"出现第一次签错人或冒名"。
- **旧工件全部补签完成后**：可以把"缺签署"从警告升级为错误，让门槛变成硬约束。
- **如果签署记录开始被手改**：说明入口不够方便，应该改入口（例如支持批量签署），而不是放宽校验。
