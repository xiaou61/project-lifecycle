# D-007 · 查看器不重新实现状态推导

## 背景

`desktop/` 是一个 Electron + TypeScript 的工件查看器：列出工作项、显示阶段和任务进度、展示审批签署和文件日期、选中文件后渲染 Markdown。它需要一个前端能直接消费的数据结构。

## 问题

最自然的做法是在 TypeScript 里读 `.agent/` 下的 Markdown，自己解析 frontmatter 和章节，渲染成界面。这条路的问题不是工作量，而是**事实源**：

状态推导（阶段判定、门槛阻塞、来源覆盖、测试证据、`code_sync` 锚点、文档体积、签署完整性）已经在 `project_status.py` 里实现了一遍，而且它的语义细节极多——例如 `state_evidence.code_sync` 只有在验证报告声明了 `verified_commit`、之后只有 `.agent/` 变动、且工作区干净时才是 `verified`。在 JS 里再实现一遍，就是 D-003 明令禁止的"两份状态"：两份必然漂移，漂移时没有第三方能判断哪份是对的，而且这次漂移发生在两种语言之间。

## 备选方案

**方案 A：前端自己解析 Markdown 并推导状态。**
被否掉：等于第二份实现，且立刻会和 Python 侧漂移（Python 加一条门槛规则，前端不会知道）。

**方案 B：前端只解析 frontmatter 和章节，不推导阶段。**
被否掉：仍然要在 JS 里复刻 `markdown_section`、frontmatter 解析和状态标签映射；漂移面小一点，但方向一样。

**方案 C：主进程调用 `project_status.py --json`，界面只渲染返回的字段。**
界面拿到的 `state`、`phase_label`、`approval`、`task` 计数全部来自那一次调用，前端没有第二套判断逻辑。

**方案 D：把状态推导从 Python 移植到 TypeScript，两边只留一份。**
被否掉：Skill 的运行时是 Agent 宿主的命令行，那里只有 Python；为了让界面省一次子进程调用而把实现搬到浏览器侧，等于让 CLI 依赖 Electron。

## 决策与理由

采用**方案 C**，并顺着它做三个具体取舍：

- **Python 是唯一的状态实现**，界面通过 `spawn` 调 `project_status.py`、`project_validate.py`、`update_history.py` 取 JSON。为此新增了 `state_label` 字段：界面需要中文状态名，而标签映射已经在 Python 的 `STATE_LABELS` 里，复制到 TS 就是又一份要同步的表（`phase_label`、`mode_label` 早就是这个先例）。
- **Markdown 渲染放在主进程**（用 `marked`），不在渲染进程。渲染进程因此不需要模块系统、不需要打包器，`renderer.ts` 没有 import/export，`tsc` 直接把它编译成浏览器能加载的普通脚本——少一个构建环节。
- **exe 内置一份脚本副本**（`--extra-resource=../skills`）。代价是这份副本会随 Skill 更新而过期，需要重新打包；换来的是 exe 开箱可用。想用实时版本就设 `PROJECT_LIFECYCLE_SCRIPTS`。

安全上的对应取舍：工件正文按 Markdown 渲染后直接 `innerHTML`，所以用 **CSP**（`default-src 'none'; script-src 'self'`）而不是引入 DOMPurify。这是原生能力覆盖依赖的例子：CSP 禁掉脚本和内联样式后，工件里混入的 `<script>` 或 `onerror=` 无法执行，不需要额外的清洗库。

## 代价和后果

- **界面依赖 Python 3.9+ 和子进程调用**。exe 不含 Python 运行时，目标机器要自己装。首屏因此有几秒等待（读多个文件、跑 `git status`、按需 `git log`）。
- **`project_status.py` 的 JSON 变成对外接口**。虽然它本来就是给 Agent 读的稳定结构（有 `schema_version`），现在多了一个消费方；改字段要按"新增字段比修改字段安全"处理。
- **渲染进程没有类型共享的模块系统**，共用形状放在 `src/types.d.ts` 的全局声明里。好处是不需要打包器，代价是不能用 `import type`。
- **exe 体积 326 MB**（Electron 的固定开销），这是选 Electron 的代价，不是应用代码的体积。

## 什么情况下该重审

- **Python 子进程成为瓶颈或不可用**（目标机器不允许装 Python）：那时才考虑把推导逻辑移植到 TS，并且必须同时删掉 Python 侧的实现，不能两边并存。
- **出现第二个非 Python 的消费方**（例如 Web 版）：把 `project_status.py --json` 的输出正式定为公开契约并加版本兼容测试，而不是各自解析工件。
- **CSP 不足以覆盖实际内容**：如果工件开始引入需要执行的内联内容（目前明确不允许），再补清洗层。
