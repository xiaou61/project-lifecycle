# D-004 · 不提供文件锁，改用 Git Worktree 隔离

## 背景

多个对话（或多个 Agent 会话）同时打开同一个项目、同一个分支、改同一批文件时，会互相覆盖、产生冲突，或者把改动错误地归到别的工作项上。

## 问题

“跨会话恢复正确事实”和“同一工作树的写入互斥”看起来是同一个需求的两面，实际上不是：

- 前者是**信息问题**：换对话后要能找回当前任务的目标、批准状态和阻塞；
- 后者是**并发控制问题**：要防止两个写入者同时改一个文件。

本项目只解决前者。如果要用工具解决后者，就必然要引入锁或自动合并，而这需要常驻进程、锁超时、死锁处理和冲突策略 —— 这是一个**独立的、比本 Skill 大得多的系统**。

## 备选方案

**方案 A：在 `.agent/` 里放一个锁文件，写入前检查。**
被否掉的原因有三个：锁不会自动释放（进程崩了就永久占住）；跨机器、跨 clone 根本不共享；而且它给出的是**虚假的安全感** —— 一个锁文件挡不住直接编辑源码的人。

**方案 B：自动合并多个对话的改动。**
被否掉：合并策略的正确性依赖语义理解，工具无法可靠做到“这处改动属于哪个工作项”。错误合并比冲突更危险，因为它是静默的。

**方案 C：诚实划界 + 用 Git 原生能力隔离。**
推荐“一项工作、一个分支、一个 Worktree、一个写入对话”：

```powershell
git worktree add "..\项目-WORK-003" -b "work/WORK-003"
```

## 决策与理由

采用**方案 C**。判断依据是：**这个问题的正确解法已经存在于 Git 里**，Skill 再去实现一遍锁，只会做出一个更差的 Git。Skill 的职责收窄到它真正独有的部分：

- 用 `workspace.md` 做**工作区归因** —— 记录 `base_commit` 和每条改动路径属于 `current_work`、`user_existing` 还是 `unknown`；
- 归因不清楚时**拒绝自动继续**，而不是猜；
- 无法使用 Worktree 时，退化成人工约定（同一目录同一时刻只允许一个写入对话），并在交接前跑 `checkpoint`。

“无法归因就停住”是这里最关键的设计：用户原有的未提交改动**不允许被覆盖、清理或提交**，即使任务文件里写着“已完成”。

## 代价和后果

- 用户要自己管 Worktree 和多分支，Skill 不会替他们建。这是明确的成本转移，换来的是不引入一个不可靠的锁。
- 归因需要用户配合：改动一多，`workspace.md` 就要维护。所以它只在**检测到脏工作区**时才要求，干净时不需要写。
- 只读场景（调查、审查、读文档）**不需要任何隔离**，可以被多对话共享。这条区分避免了把隔离要求泛化到所有场景。

## 什么情况下该重审

如果出现同一目录下多写入者的**真实高频**场景（例如多人共用一台开发机上的同一个 clone），并且 Worktree 因为环境限制不可用，那时才值得讨论轻量的协作协议。但即使如此，也应该优先解决环境限制（让 Worktree 可用），而不是在 Skill 里加锁。
