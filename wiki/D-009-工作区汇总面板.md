# D-009 · 工作区级是汇总面板，不是图谱

## 背景

需求是"做一个总的图谱"，单个项目也要能跳进去。D-008 已经把工作项内部的追踪图谱做出来了（REQ/AC/TASK 三条带），这一篇记录往上一层——工作区级——为什么做成了汇总面板而不是图。

## 问题

先查真实数据：`F:\AIAM开发\.agent` 是一个真实的多仓库工作区（有 `PROJECT-INDEX.md`，没有 `changes/`），下面 4 个项目共 **11 个工作项**。够多，值得有总览。

但"工作区级的图"有两个硬问题：

1. **项目之间没有可推导的边**。项目不互相引用，`related_to` 只在工作项之间。画成图只会是一堆孤立节点——图的价值全在边上，没有边就没有图。
2. **项目清单从哪来**。工作区级汇总必须先知道有哪些项目，而"项目清单"本身是一个需要决定的数据来源。

## 备选方案

**方案 A：工作区级也画成图。**
被否掉：没有边。要让它成图，得先在 `PROJECT-INDEX.md` 里声明项目之间的关系（共享模块、上下游），这是先有数据再有图。

**方案 B：扫描某个父目录下所有含 `.agent/` 的目录。**
被否掉：扫描范围无法界定（`F:\` 下有几十个目录），会把无关项目、临时克隆和废弃目录一起列进来；而且"扫到了"不等于"这个项目归我管"。

**方案 C：只认工作区的 `PROJECT-INDEX.md`，没有就不给工作区视图。**
被否掉：绝大多数项目没有外层工作区（本机 7 个受管项目里只有 1 个有）。这会让功能对大多数用户不可用。

**方案 D：汇总面板 + 双来源清单（索引优先，应用清单兜底）。**
采纳。工作区级是**数字**不是图：项目数、工作项数、需要处理数、待补签工件数、缺证据验收数，加每个项目一张卡片。

## 决策与理由

采用**方案 D**，配套四个决定：

- **工作区级回答"哪个项目需要我管"，不回答"谁依赖谁"**。所以是卡片加计数，不是图。点卡片进入该项目（这就是"单个项目也要能跳进去"）。
- **清单来源按顺序尝试**：先看当前目录的 `.agent/PROJECT-INDEX.md`，再看父目录的（这样直接打开工作区里的某个项目也能发现整个工作区），都没有才用应用自己记住的清单（**选择项目** 会往里加，卡片上有"移出清单"）。界面明确写出清单来自哪里，不让人猜。
- **索引解析只取「项目清单」表的源码目录列**，路径相对工作区根解析。解析在 Electron 主进程做——这是读一个导航索引，不是推导生命周期事实，所以不违反 D-003/D-007。
- **汇总只是对已推导事实计数**：每个项目的数字全部来自 `project_status.py --json` 的字段（`state`、`approval.unsigned`、`traceability.acceptance_without_evidence`），主进程只做相加，不产生新语义。
- **直接打开工作区导航目录时自动进工作区视图**，不显示"这个项目还没有工作项"——`scope: workspace` 的目录按设计就没有工作项，那不是错误。

## 代价和后果

- **N 个项目 = N 次 Python 调用**。并发发起，4 个项目约 1 秒；项目多时会线性变慢。真要上百个项目需要缓存或 Python 侧批量模式，现在不做。
- **"最后活动"取不到就是取不到**：优先 Git 提交时间，其次 `updates.md` 最后一条记录，两者都没有就显示"没有提交记录，也没有更新历史"（`opensandbox-opencode-poc` 就是这种，它列在索引里但从未初始化）。不用文件 mtime 兜底——目录 mtime 在文件被修改时不会变，用它等于给一个不可靠的数字。
- **索引里登记但没初始化的目录也会出现在列表里**，显示 0 个工作项、规范待确认。这是诚实的呈现，不是过滤掉。
- **应用清单会累积**，所以卡片上必须有"移出清单"；上限 30 条。
- **汇总数字会放大焦虑**：本机 4 个项目一次显示 29 个待补签工件、36 个缺证据验收。这是真实状况，但读者要知道这两个数字都来自"新加的规则遇到旧工件"，不是 29 个独立的失误。

## 什么情况下该重审

- **项目数超过约 20 个**：需要缓存或 Python 侧批量模式，否则打开工作区会明显变慢。
- **`PROJECT-INDEX.md` 开始声明项目间关系时**：那时工作区级可以真的画成图，边从索引来而不是从推测来。
- **出现"一个项目属于多个工作区"的情况**：当前清单来源是"找到第一个就用"，需要改成显式选择。
- **想按人/团队过滤时**：现在是全量汇总，没有归属维度；那需要工件里先有负责人字段（见 D-006 关于审批人名单的重审条件）。
