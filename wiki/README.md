# 设计 wiki

这里记录 `project-lifecycle` **当初为什么这样设计**、考虑过哪些别的做法、以及改动某一处会连带破坏什么。

目标项目里对应这个职责的位置是 `.agent/notes/`（跨工作项仍有效的决策理由）。本仓库自己过去没有对应位置，设计理由散落在 `CHANGELOG` 的“决策”字段和 commit message 里，本目录就是为补这个空位而建。

## 这里放什么，不放什么

| 问题 | 去哪里 | 为什么 |
| --- | --- | --- |
| 怎么安装、怎么用、命令怎么写 | [`docs/`](../docs/index.md) | 面向用户的正式教程，随站点构建和部署 |
| 哪天改了什么、依据和验证是什么 | [`CHANGELOG.md`](../CHANGELOG.md) | 追加式时间线，回答“什么时候定的” |
| 运行时不可绕过的规则和门槛 | [`skills/project-lifecycle/references/`](../skills/project-lifecycle/references/workflow.md) | Agent 执行时读取的协议，是行为规范 |
| **当初为什么这么定、备选是什么、改它会怎样** | **本目录** | `CHANGELOG` 只记结论，不展开取舍 |
| 为什么有些事它不负责 | [`docs/reference/boundaries.md`](../docs/reference/boundaries.md) | 边界问答，偏用户视角 |

写进这里的门槛只有一条：**从代码和现有文档里推不出来的内容才写**。能被源码直接读出来的事实不要复制到这里，否则就是第三份需要同步的副本。

## 什么时候写一篇

- 一个决定**否决了看起来更简单的做法**，后来的人可能想再试一次；
- 一个字段或规则的语义**容易被误读**（例如 `pending` 不是批准），改掉它会让下游失效；
- 一个能力被**明确划到范围外**，需要留下理由，避免反复被提起；
- 一处实现看起来**啰嗦或绕**，其实是某个约束逼出来的。

不写的内容：单次性的实现细节（看代码和 commit 即可）、能从 `CHANGELOG` 直接读到的账、以及流水账式的开发日志。

## 写法

每篇按同一结构：**背景 → 问题 → 备选方案（含被否掉的）→ 决策与理由 → 代价和后果 → 什么情况下该重审**。最后一项很重要：它不是“永不变更的教条”，而是写明失效条件，将来重新讨论时有依据。
