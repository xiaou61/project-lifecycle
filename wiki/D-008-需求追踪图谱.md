# D-008 · 需求追踪图谱只画工件里写下的引用

## 背景

需求是让 REQ/AC/TASK 这些标识也能"关联起来"，并做一个总的图谱，单个项目/工作项也能跳进去。

## 问题

图谱能画什么，完全取决于工件里**真实写下了什么**。先摸清真实数据的形态（3 个项目、7 个工作项）：

| 事实 | 数据 |
| --- | --- |
| REQ/AC/TASK 标识普遍存在 | 35 REQ、35 AC、47 TASK |
| 任务级依赖普遍存在 | 39 条 `- 依赖：` 边 |
| `- 对应：` 把任务映射到 REQ/AC | 47 条 |
| REQ↔AC 的**直接**关联 | 只有 1 个工作项有（来源覆盖表，16 条边） |
| AC → 结构化测试证据 | **0 条**（所有报告都缺证据表，这正是它们全部卡住的原因） |
| 项目与项目之间的关联 | **0 条** |

三个设计难题：

1. **id 只在工作项内唯一**。每个工作项都有自己的 `REQ-001`。不加命名空间就会把不同工作项的同名需求并成一个节点。
2. **全量连线是面条**。一个工作项就有 8 REQ + 9 AC + 12 TASK，加上任务依赖是 70+ 条边。一个项目 4 个工作项就是 250+ 条。
3. **"总的图谱"在最外层没有边可画**。项目之间不互相引用，工作区级画成图只会是一堆孤立节点。

## 备选方案

**方案 A：前端自己解析 Markdown 建图。**
被否掉：D-007 已经否过一次同类做法。追踪解析有四种定义写法、区间语法和旧版标记，在 TS 里再实现一遍必然与 Python 侧漂移。

**方案 B：按编号顺序推断 REQ↔AC 的对应。**
被否掉：`REQ-006~REQ-008` 与 `AC-006~AC-009` 看起来对应，但那是**猜的**。真实数据里 AutoTest 的 `AC-001` 同时挂在 5 个不同 REQ 下，编号根本不一一对应。图是给人做判断用的，画出猜出来的边比不画更糟。

**方案 C：只画工件里显式写下的引用，连线默认隐藏、悬停才亮。**
采纳。边只有三个来源：任务的 `- 对应：`、任务的 `- 依赖：`、来源覆盖表里的 REQ↔AC 配对。

**方案 D：工作区级也画成图。**
被否掉：没有可推导的边。工作区级应该是**汇总**（每个项目的阻塞数、待补签数、证据缺口），不是图。

## 决策与理由

采用**方案 C**，配套五个具体决定：

- **推导在 Python**（`project_status.py` 的 `traceability` 块），前端只画。与 D-003/D-007 一致：状态和派生事实只有一份实现。
- **解析要认下真实存在的写法**，而不是要求工件改成规范写法——旧工件不会因为工具升级被重写：
  - 四种定义写法：`- **REQ-001 标题**：`、`- **AC-001** 标题：`、`- **AC-001**：描述`、`- REQ-001：描述`（Code-Nest 用的是最后一种，没有粗体）；
  - 区间语法 `AC-006~AC-009`（第二段可省略前缀），单次扫描展开，顺序与原文一致；
  - `旧版` 前缀：只标记不判定，因为它说明该 id 来自更早的修订，判定规则不明确；
  - `对应` 与 `依赖` **写在同一行**（Code-Nest 的 `- 对应：…；依赖：…`）：先按 `；` 切段，切不开时两个键各自匹配（这里必须是两个 `if`，用 `if/elif` 会让后者永远解析不到——这个 bug 是在真实项目上跑出来的）。
- **id 加工作项命名空间**。图里的节点 key 是 `WORK-001/REQ-001`，跨工作项引用必须带 `work_id`。
- **连线默认几乎不可见（opacity 0.05），悬停亮出该节点的关系，点击把关系写成文字**。这是唯一能同时容纳 70 条边和可读性的做法；也给不出"所有关系"的假象——想看得自己指过去。
- **把缺口也画出来**：未映射到需求的任务、无结构化证据的验收、引用了未定义需求的 id。这是图谱最有用的一部分——AI测试平台 WORK-001 一眼就能看出 9 个验收标准全都没有结构化证据。

## 代价和后果

- **图谱完整度取决于工件写得多细**。没写 `- 对应：` 的任务就是孤立节点，工具不会替它补。AI测试平台 WORK-004 的 3 个任务全都没有 REQ/AC 可映射（该工作项本身也没定义 REQ/AC）。
- **REQ↔AC 直连边在多数项目里是空的**，因为来源覆盖表是可选的。7 个工作项里只有 1 个有。没有它时，REQ 与 AC 只能通过任务间接关联——图上就是这么呈现的，不做补偿。
- **AC → 测试证据的边目前全空**。报告写的是散文式"AC-001：通过"，不是结构化矩阵。工具不把散文当证据（`testing.md` 的既有规定），所以图上所有 AC 都标黄。
- **不做力导向布局**。按类型分层（REQ / AC / TASK 三条带）是确定性的，同一份工件每次画出来一样，便于对照；代价是节点超过约 40 个时带宽会溢出，需要靠筛选而不是自动布局解决。
- **悬停才亮线意味着截图和打印看不到关系**。这是可读性换来的，自检里用真实事件派发覆盖了这条路径。

## 什么情况下该重审

- **来源覆盖表普及后**：REQ↔AC 直连边会变多，那时可以考虑把"直连"和"通过任务间接关联"分开着色（目前直连是绿色虚线）。
- **验证报告开始写结构化证据表后**：可以补上 AC → 证据的边，让验证门从"缺证据"变成"证据在此"。
- **工作区级真要成图时**：需要先让 `PROJECT-INDEX.md` 声明项目之间的关系（共享模块、上下游），否则画不出边。这是先有数据再有图，不是先画图。
- **单个工作项的节点数超过约 40 个时**：需要加筛选（只看未映射任务 / 只看无证据验收），而不是换成力导向布局。
