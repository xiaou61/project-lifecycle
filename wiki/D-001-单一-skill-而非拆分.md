# D-001 · 保留一个总 Skill，而不是拆成多个

## 背景

同一时期流行的做法（如 Superpowers）是把开发方法拆成一组可组合的 Skills：需求一个、设计一个、调试一个、验证一个，各自带脚本和触发词。这个做法在本项目设计时被认真考虑过，最终没有采用。

## 问题

如果按阶段拆分，每个 Skill 都要独立判断“现在能不能往下走”。而“能不能往下走”依赖的恰恰是**跨阶段共享的状态**：

- 需求有没有被批准 —— 设计和任务拆分都要看；
- 上游是否发生了漂移 —— 需求一改，方案、设计、任务全部失效；
- 硬依赖是否完成 —— 实现和验收都要看；
- 工作项当前在哪个阶段 —— 决定这次该写哪个工件。

这套判断一旦分散到多个 Skill 里，就会出现两份互相矛盾的结论。

## 备选方案

**方案 A：按阶段拆成多个 Skill。**
好处是每个 Skill 短、触发词清晰、可以独立演进。代价是每个 Skill 都要自带一套门槛检查逻辑，而这些逻辑必须保持一致；一旦某个 Skill 升级了漂移规则，其余的不会自动跟上。

**方案 B：一个总 Skill + 多个可组合动作。**
用户侧只有一个入口，动作是 `init` / `status` / `resume` / `validate` / `history` / `updates` / `record` / `checkpoint` / `push-check`；阶段规范作为参考文件按需读取，不单独成为可触发实体。

**方案 C：一个 Skill 加多个“同名近似”Skill 覆盖窄场景。**
这是最差的选项：触发词高度重叠，Agent 会在多个近似 Skill 之间摇摆，状态进一步分叉。

## 决策与理由

采用**方案 B**。核心判断是：**可以被独立批准或独立验收的边界，才值得独立成一个实体**。需求和设计不能被独立验收（设计错了但需求没变，是设计本身要改），所以它们不应该各自拥有独立的门槛判定权，而应该是同一套状态机里的不同阶段。

`SKILL.md` 里保留两个显式约束，正是这个决策的落地：风险模式（`lite`/`managed`/`strict`）和参考协议（`compact`/`full`、需求深挖）都**不拆成会互相抢触发的重复 Skill**。

## 代价和后果

- `SKILL.md` 必须保持短，详细协议外溢到 `references/*.md`；这带来一个纪律要求：入口只放底线和路由，不能把规范复制进来。
- 单文件会变大：`project_status.py` 已经 1671 行，因为阶段推导、关系解析、Git 归因、恢复包都在同一个状态机上。这是刻意接受的代价 —— 拆开这些函数会立刻产生跨文件状态共享问题。
- 新增一种工作模式时，只能扩展现有的模式枚举和参考文件，不能新建 Skill。

## 什么情况下该重审

如果出现一个**可以被独立批准、独立验收、且与现有阶段无共享状态**的新能力时，它应该独立成 Skill，而不是继续塞进这里。反过来说，任何“只是流程更长一点”的需求都不构成拆分理由。
