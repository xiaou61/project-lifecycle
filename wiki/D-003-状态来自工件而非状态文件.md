# D-003 · 状态从工件推导，不建状态文件

## 背景

一个跨会话的助手系统，直觉上应该有一个 `state.json` 或 `.agent/current.md` 保存“当前在哪一步”。本项目明确禁止这样做。

## 问题

状态文件看起来省事，但它引入了**两份状态**：一份是人工或 Agent 写入的状态文件，另一份是工件本身的真实内容（需求是不是真批准了、任务是不是真做完了、测试是不是真跑过）。这两份必然漂移，而且漂移时**没有第三方能判断哪份是真的**。典型失败：

- 状态文件写“已完成”，但 `testing/report.md` 还是空的；
- 任务标记 `done`，但代码根本没改；
- 需求被改过，状态文件还停在“设计已批准”。

## 备选方案

**方案 A：单一 `state.json`，工件只是附件。**
被否掉：工件变成二级信息，用户会先去改状态文件而不是工件，漂移无法收敛。

**方案 B：状态文件 + 工件，靠一致性校验兜底。**
被否掉：这只是把漂移检测的成本转嫁给用户，而且校验器本身也会成为第三个需要维护的事实源。

**方案 C：不存状态，每次从工件和 Git 现算。**
`project_status.py` 每次读取 `requirements.md`、`proposal.md`、`design.md`、`tasks.md`、`testing/report.md` 的 frontmatter 和结构化段落，实时推导阶段、阻塞、下一步。

## 决策与理由

采用**方案 C**。工件是唯一事实源，状态是**投影**而不是存储。这样“状态错了”必然意味着“工件写错了或没写”，修正方向唯一，不存在两份记录互相对不上的情况。

这个决策还顺带解决了上下文压缩问题：对话历史会被压缩、摘要会失真，但工件不会。所以恢复时读取的是 `requirements.md` 里的目标、验收标准和约束，而不是聊天摘要。

配套的设计是**每次现算都必须诚实标注边界**，这体现在两个字段上：

- `state_evidence.documented_state` 只是**工件推导结果**，不代表代码已经这样；
- `state_evidence.code_sync` 只有在 `testing/report.md` 写了 `verified_commit`、且该提交之后没有源码改动、且工作区干净时才是 `verified`；缺锚点是 `unknown`，锚点之后有源码改动是 `stale`，格式错误是 `invalid`。

只要不是 `verified`，`requires_reconciliation` 就是 `true` —— 工具不会替用户宣布“代码和 Markdown 已同步”。

## 代价和后果

- **每次查询都要做真实 IO**：读多个文件、跑 `git status`、必要时跑 `git diff`。这比读一个 JSON 慢，但换来的是不会说谎。
- **推导逻辑必须能表达“不知道”**：`unknown` / `stale` / `invalid` 这些值不是装饰，如果省略它们，工具就会被迫在信息不足时猜一个结论。
- **`resume` 的 JSON 结构变更影响面大**：集成方按 `schema_version` 和字段读取，所以新增字段比修改字段安全。当前 `schema_version` 是 `2`。
- 文档体积会拖慢恢复，所以加了**软警告**（单文件 > 20,000 bytes、总量 > 80,000 bytes、核心文件 > 6 个）。注意是警告不是错误：它提示你把长日志挪到证据文件，而不是自动删你的内容。

## 什么情况下该重审

如果工件数量和体积增长到“现算”明显拖慢每次交互（而不是仅仅触发软警告），可以考虑**缓存推导结果**，但缓存必须带失效依据（例如绑定的 commit 和文件 mtime），且缓存缺失时必须能退回现算 —— 不能演变成一个新的状态文件。
