# D-005 · Python 版本下限：支持 3.9，而不是把门槛提高到 3.10

## 背景

命令适配器 `project-lifecycle.ps1` 按 `py -3`、再 `python` 的顺序解析解释器，把底层脚本的实现细节藏在统一入口后面。仓库里同时存在 cpython-39、cpython-311、cpython-314 三份字节码缓存，说明这个仓库被多个 Python 版本跑过。

2026-09-15 跑测试时发现：本机 `python` 解析到 3.9.13，44 个测试里 5 个失败，`init` 命令完全不可用。根因是两层版本不兼容叠在一起，第一层把第二层遮蔽了：

1. `init_project.py` 第 45 行是一行 515 字节的中文文本，而文件没有编码声明。Python 3.9 的 tokenizer 在无声明状态下遇到单行超过 512 字节的非 ASCII 内容会误判编码，编译期直接抛 `SyntaxError: Non-UTF-8 code starting with '\xe5'`。二分验证：同一内容拆成多行正常，纯 ASCII 600 字节正常，阈值就在 512 字节，且与所在行号无关。
2. 绕过第一层后暴露 `Path.write_text(..., newline="\n")`——`newline` 参数是 3.10 才加入的，共 4 处。

## 问题

仓库从来没有声明过最低 Python 版本，也没有任何地方校验它。适配器的回退链会主动选中旧解释器，于是“支持哪些版本”这件事既没有写下来，也没有被机械检查过。用户看到的不是“版本不够”，而是一个指向源码编码的 SyntaxError——完全无法据此定位。

## 备选方案

**方案 A：声明最低版本为 3.10，加版本守卫和文档说明。**
被否掉的原因是它把代价转嫁给用户而不是消除它。本机回退到的正是 3.9，提高门槛后 `init` 在这类机器上仍然失败，只是错误信息变清楚了。而修好它只需要 5 处等价改写。

**方案 B：只加编码声明，不碰 `write_text`。**
被否掉的原因是不够：它只修掉第一层，`init` 会在下一行继续以 `TypeError` 失败。只修看得见的那个症状，等于把 bug 挪了个位置。

**方案 C：支持 3.9——补编码声明，并把 4 处 `write_text(..., newline="\n")` 换成 `write_bytes((...).encode("utf-8"))`。**
`encode` 之后写字节，与 `newline="\n"` 的效果逐字节相同（都绕过换行翻译、保留 LF），且 `write_bytes` 自 3.5 起就存在。

**方案 D：保留 `write_text`，去掉 `newline` 参数。**
被否掉的原因是会静默改变输出：Windows 文本模式会把 `\n` 翻译成 `\r\n`，生成的工件换行风格随平台漂移。

## 决策与理由

采用**方案 C**，并把“支持哪些版本”从隐含假设变成两处显式约束：

1. **代码里**用方案 C 的 5 处改写，把下限落到 3.9，不引入任何行为变化；
2. **入口处**在 `project-lifecycle.ps1` 增加版本守卫，低于 3.9 时报出解析到的版本和解释器名，让失败点从“源码编码”回到“版本要求”；
3. **持续约束**交给 CI：`python-version: ["3.9", "3.11", "3.13"]` 固定下限和较新版本，任何再次引入的 3.10+ 写法都会立刻变红。

第 3 条是这次真正的修复。前两条只解决当下这一个 bug，而 bug 的类别是“环境假设既没声明也没校验”——只有机械门能阻止它复发。测试会在导入阶段加载全部 5 个脚本，因此任何一行超过 512 字节的非 ASCII 内容都会在 3.9 的 job 上立刻失败，不依赖该行是否被测试覆盖。

版本守卫刻意不用 `$LASTEXITCODE` 判断成败：在没有前置原生命令时它是 `$null`，`$null -ne 0` 为真会把正常情况误判为失败。改为先判空、再比较版本号。

## 代价和后果

- 3.9 已于 2025 年 10 月停止维护，为它维持兼容意味着不能用 3.10+ 的写法（例如 `match`、`zip(strict=)`）。当前代码里没有这类构造，代价暂为 0，但会随生态演进而上升。
- `write_bytes(x.encode("utf-8"))` 比 `write_text(x, encoding="utf-8", newline="\n")` 少一层语义：前者声明“写这些字节”，后者声明“按 UTF-8 写文本且不翻译换行”。读代码的人需要知道两者等价，这一点只在 `D-005` 和 `init_project.py` 的头部说明里。
- 必须给 `init_project.py` 补编码声明，而不能删掉那行长文本——后者只是把内容改短，同样的坑会在下一次有人写长段落时重现。声明编码是对整类问题的关闭，不是对单行的绕过。
- CI 增加了 3 个 Python 版本的矩阵和一个独立的 docs job，push 和 PR 都会跑，这是本次新增的唯一持续成本。

## 什么情况下该重审

当下游约束开始要求 3.10+ 的写法（例如确实需要 `match` 或 `zip(strict=)`），或者维护者与用户已经不再使用 3.9 时，应当把下限提高：改 CI 矩阵、改守卫里的版本号、删掉 `init_project.py` 的编码声明，并把 `write_bytes` 换回 `write_text(..., newline="\n")`。判断依据是实际使用面的收缩，而不是“3.9 已经 EOL”这条理由本身——EOL 只说明不再有安全更新，不说明没有人在用。
