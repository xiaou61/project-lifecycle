# 需求深挖访谈

这是需求阶段的可选增强模式，由本 Skill 自己定义，不依赖外部 Skill、插件或运行时。用户说“把需求问透”“详细调查需求”或“先访谈再生成 PRD/Task”时启用；普通需求和低风险修复不强制长问卷。

## 目标和边界

- 只追问会改变交付结果的用户决策，不让用户选择普通实现细节。
- `requirements.md` 就是本项目的 PRD；访谈中持续更新，不另建同内容的 `prd.md`。
- 访谈完成不等于批准。用户确认最终摘要后，才能把需求标为 `approved`。
- `compact` 可在需求批准后生成任务草稿；`full` 仍须经过方案和设计批准。

## 逐轮执行

1. 按 [workflow.md](workflow.md) 恢复规则、状态、工作项和 Git 归因，再查代码、配置、接口、测试和正式资料。
2. 将信息分为：可查到的事实、必须由用户决定的范围/行为、Agent 可自行决定的实现选择。
3. 只对第二类提问；说明推荐选项、用户可见差异和实际影响。一轮只问一个问题，支持结构化选项时提供 2～4 个选项并保留自定义入口。
4. 用户回答后先确认结论，马上写入 `用户决定`、移除对应 `待确认问题`，再计算下一分支。事实调查不能伪装成用户问题，也不能用旧聊天代替工件。

## 词汇与场景

含义模糊、存在多个叫法或会跨工作项复用的业务词汇，先给出候选定义，再用一个“触发条件 → 用户可见结果”的场景核对；确认后写入 `requirements.md` 的 `## 术语与边界` 或稳定规格。源码、规格和用户描述冲突时，先报告并暂停受影响决策。

整理已有讨论和先访谈是两种动作：前者只补会改变范围或验收的缺口，后者才使用本文件的逐轮模式。访谈结束后两者都要经过最终需求确认。

## 决策树与检查维度

只保留会改变结果的节点，并记录用户可见差异、前置事实/决策和状态 `waiting`、`askable` 或 `resolved`。未回答或依赖未确认事实的问题继续阻塞；持久化时只把真实未决项写入 `requirements.md` 的 `## 待确认问题`。

按相关性检查：

- 目标用户、触发场景、期望结果；
- 范围、非目标、是否拆分工作项；
- 主/异常流程、权限安全、失败后的可见结果；
- 数据归属、持久化、外部集成、公共接口；
- 性能、兼容性、部署、迁移、回滚硬约束；
- 验收场景、测试证据和完成定义。

## 停止条件与输出

只有决策树无 `askable` 节点、相关事实已核对、目标/范围/非目标/流程/边界/验收已写入 `requirements.md`、`REQ-*`/`AC-*` 和来源覆盖稳定、关系已检查且没有阻塞问题时，才请求最终确认。

摘要至少包含目标、范围、非目标、关键流程、约束、验收和后续流程。确认后：`compact` 生成任务草稿并等待计划确认；`full` 进入方案阶段。新增目标、接口、数据、安全、部署或架构要求时，回到最早受影响阶段并使下游失效。
