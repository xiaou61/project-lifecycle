# 自然语言执行与跨对话接力协议

本文件是受管理工作项的标准执行协议：它定义自然语言触发、每轮动作和跨对话恢复；各阶段工件的写法仍由对应参考文件负责。

## 核心约定

- 用户用自然语言即可；低风险、边界清楚的孤立改动走短路径。
- `WORK-*` 是稳定定位键，不是代码命令，也不代表批准。
- `.agent/` 工件是事实源；聊天、时间戳和记忆不能代替状态。
- 开始时选择一次风险模式：`lite` 只走短路径，`managed` 使用 `workflow: compact`，`strict` 使用 `workflow: full`；风险上升只能升级，不能降级绕过门槛。
- `.agent/INDEX.md` 只做模块/资料导航；外层 `PROJECT-INDEX.md` 只导航多仓库。
- 换会话、上下文压缩或用户说“继续”时，先恢复规范和状态；用户明确批准后才能跨阶段门槛。

## 常见借口与反驳

| 借口 | 为什么站不住 | 该做什么 |
| --- | --- | --- |
| 用户说了“继续”，等于批准了 | “继续”“开始做”只表达动作意图，除非同句明确批准 | 停在最早未批准的门槛并说明差什么 |
| 上下文压缩了，但我记得批准过 | 聊天和模型记忆不是事实源，压缩后记忆不可靠 | 重新读工件，以 `status` 与签署字段为准 |
| 状态显示已完成，那就是完成了 | `state` 是工件投影，不是源码扫描结果 | 核对任务、diff 和测试，再看 `code_sync` |
| 就在当前目录改，省得开 worktree | 同目录多写入方会互相覆盖，改动还会归错工作项 | 首次实施前问一次，按用户答复执行 |
| 顺手把别人的未提交改动一起提了 | 用户已有与未知归属的改动必须原样保留 | 只提交当前工作项归属的文件 |
| 用户说“存一下”，那就能推了 | 本地保存不推断远端授权 | 推送、tag、部署要用户明确要求 |

## 风险模式

`lite`、`managed`、`strict` 的适用范围、必要记录、允许的验证和"只能升级不能降级"的判据只在 `SKILL.md` 的「风险路由」维护，本文件不重复。

`requirements.md` 可以记录 `mode` 和 `mode_reason`。旧工件没有 `mode` 时，状态查询按 `workflow: compact -> managed`、`workflow: full -> strict` 兼容推导。显式 `mode` 非法或缺少理由只产生警告；`validate --strict` 才会把这些兼容性警告视为失败。

## 用户如何触发

| 用户表达 | 当前动作 | 持久结果 |
| --- | --- | --- |
| “我有个想法”“想加功能” | 讨论范围、约束和验收 | 稳定后创建 `requirements.md` |
| “把需求问透”“先访谈再出 PRD/Task” | 进入 `requirements.md` 的「需求深挖」逐轮模式 | 持续更新需求，最终确认后进入流程 |

| “方案可以，做设计” | 批准方案并完成设计 | `design.md` |
| “设计没问题，拆任务” | 批准设计并拆执行计划 | `tasks.md` |
| “按计划开始做”“实施 WORK-003” | 恢复状态，门槛满足后实现 | 源码、测试和任务状态 |

| “存一下”“留个检查点” | 确认改动归属并创建本地 commit | 本地 commit（需用户授权） |
| “归档一下”“清一下列表” | 把已完成的 `WORK-*` 移进 `changes/archive/` | 目录迁移，文件内容不变 |
| “推送后核对一下” | 用 `git status`、`git log` 与远端跟踪分支核对 | 默认只读 |

显式写 `$project-lifecycle` 总能请求本 Skill；孤立小修复不必强行创建工作项。

## 规则层级与优先级

三个范围，越具体越不能突破上层：

- **Skill 全局底线**写在 `SKILL.md`：从工件恢复事实、不自行批准阶段、重大范围变化回到最早工件、不覆盖用户资料、不伪造未运行的证据、小改动走短路径。项目文件不能静默放宽；要改变行为就改 Skill。
- **项目常驻规范** `.agent/rules/always.md` 记录跨工作项长期有效的事实和约束（技术栈、真实路径、检查命令、接口/安全/部署要求、生成目录边界）。初始化器只建目录、不猜规则；首次使用先检查仓库并向用户提草案，确认后写 `status: active`、`configured: true`。规则未确认时可以做只读讨论、设计和验证，不能实现、部署、迁移或变更数据。
- **工作项约束**只写在 `requirements.md`：本次更严格或额外追加的约束，不重复项目规则，也不悄悄豁免。

冲突时按以下顺序取更具体者：

```text
AGENTS.override.md
  > AGENTS.md
  > .agent/rules/always.md
  > 当前工作项 requirements.md
  > proposal.md / design.md / tasks.md
```

只有冲突可能影响目标、验收、公共行为、接口、数据、安全、部署或架构时才停；已批准范围内的局部事实修正可记录理由后继续，不确定且有实质影响时只问一次。

用户愿意在项目里固定签署人时，在 `always.md` 的 frontmatter 写 `approver: <姓名>`；`approve` 省略 `--by` 时用它填签署人。**它只提供身份，不提供批准**：是否批准仍取决于用户当轮是否明确确认，模型不能因为这个默认值自行调用 `approve`。

## 每轮固定顺序

1. **确定项目**：多仓库先读外层 `PROJECT-INDEX.md` 和项目映射，再读目标项目的 `AGENTS.override.md`、`AGENTS.md` 和说明；需要定位模块时再读项目 `.agent/INDEX.md`。
2. **恢复规范**：读 `.agent/rules/always.md`。文件缺失、草案、无效或冲突时先查仓库并提出草案；可以继续只读讨论和不依赖未知规则的设计/验证，但实现、部署、迁移和数据变更必须等待确认。
3. **查询状态**：通过已安装 Skill 的统一命令入口运行（`$lifecycle` 的解析规则见 `SKILL.md` 顶部）。不要把底层 Python 文件相对当前项目解析，也不要从目标项目的 `.agent/scripts/` 查找状态或校验脚本：

   ```powershell
   & $lifecycle brief <project-root> --json      # 每轮默认：只含活动工作项、阻塞、下一步
   & $lifecycle status <project-root> --json     # 完整清单、签署、依赖、预算、全部警告
   & $lifecycle resume <project-root> --work WORK-003 --json
   ```

   默认用 `brief`：完整 `status` 在 16 个工作项的项目上约 225 KB，只为一次上下文切换不值得。`brief` 保留每项的 `warnings`（真阻塞）与 `hygiene`（文档体积、任务格式等整理项）分开的两组提示。

   `--resume` 返回 `auto_resume`、`ask_user` 或 `out_of_scope`，并给出阶段、阻塞、建议读取路径和接力提示。选中的 `work_item` 还会从 `requirements.md` 带出 `goal`、`acceptance_criteria`、`constraints` 和 `goal_status`；缺失时返回恢复警告，不得根据聊天摘要臆造。`state_evidence` 明确区分工件推导状态、已记录测试、Git 快照和未知的源码同步情况；它不能证明代码已完成，恢复后仍需核对任务、差异和测试。下游按 `schema_version` 和字段读取，不解析中文文本。
4. **定位和加载依据**：按用户点名的编号、中文名、内容唯一匹配、唯一活动项的顺序选择；先读需求，再按阶段读取已批准工件、规格和共享资料。
5. **检查门槛并执行一个动作**：核对规范、批准、硬依赖、关联影响和工件一致性；然后讨论、写当前工件、改代码、验证，或停在真实确认点。
6. **同步事实**：只按实际结果更新工件和任务状态；需要接力或暴露阻塞时再输出状态。变更历史以 Git 提交信息为准。

发布或交接前可运行：

```powershell
& $lifecycle validate <project-root> --json
```

它检查结构、标识符、来源引用和测试证据。普通 `validate` 保留警告并允许继续查看结果；`--strict` 将兼容性警告视为失败。两者都不会自动运行冒烟测试。

## 工作区与多仓库边界

恢复前查看状态输出中的 Git 概览。**未提交改动不阻塞恢复**——工作区归因表（`workspace.md`）机制已于 2026-10-10 按用户要求停用：它要求每个工作项都登记工作区里的**全部**未提交路径，成本是"工作项数 × 改动路径数"份重复登记，而且只是一张很快过期的快照。未提交的改动由 Git 自己记录，status / resume 不再要求任何登记文件。

提交时仍遵守一条纪律：**只提交当前工作项归属的文件，用户已有与未知归属的改动保持原样**；不得因为聊天或任务文件说“完成”就覆盖、清理或提交未授权改动。存在并发写入时，优先用 `git worktree` 隔离，或遵守"同一目录同一时刻只允许一个写入对话"。

外层 `.agent/` 不承载项目状态；进入开发、验证或恢复 `WORK-*` 时必须切换到真实项目目录。初始化器创建项目内 `.agent/INDEX.md`：索引登记源码、配置、测试、规格和工作项的位置，不记录阶段或任务状态。

## 阶段门槛

`requirements.md` 的 `workflow: compact` 允许省略 proposal/design，只保留批准需求、任务计划和验证报告；不得用它绕过安全、迁移、公共接口或架构所需的设计。`managed` 只是记录和阶段的精简，不是安全例外；一旦风险上升就升级到 `strict`。

| 当前事实 | 当前阶段 | 允许的动作 |
| --- | --- | --- |
| 需求不存在或为 `draft` | 需求讨论 | 澄清、修订并等待确认 |
| 需求已批准，提案缺失/`draft`/`stale` | 方案选择 | 创建或修订提案并等待确认 |
| 提案已批准，设计缺失/`draft`/`stale` | 详细设计 | 结合真实代码完成设计 |
| 设计已批准，任务缺失/`draft`/`stale` | 实施计划 | 拆可独立验证的纵向切片并等待确认 |
| 任务已批准且有未完成任务 | 开发实现 | 无硬依赖和规范阻塞时改代码并同步任务 |
| 任务完成但没有通过验证报告 | 测试验收 | 记录证据、缺口和风险 |
| 上游一致、任务完成、验证通过 | 完成沉淀 | 核对规格和遗留事项并可选归档（归档前修正旧路径引用，见「稳定规格」） |

在“开发实现”阶段，批准一次计划后可连续执行到每个任务自己的验证为止，不必每完成一个任务就停下汇报；遇到范围变化、验证失败或新的决策点再停。

`strict` 工作项在实现阶段还会收到一条不阻断的提示：`tasks.md` 缺少 `## 评审焦点`。它提醒的是"规格暗示、却没有任务测试覆盖的失败模式"，格式与归属规则见 [tasks.md](tasks.md)。工作项已 `passed` 后不再提示——回头补历史计划不会改变已发生的事。

本表里的“已批准”指工件 `status: approved` 且带签署记录；只有 `status` 没有签署时按“未完成签署”处理，先补签再跨门槛。

如果后期工件存在但更早阶段缺失、未批准或失效，回到最早受影响阶段。用户可以明确合并或豁免门槛，但决定必须写入受影响工件，不能从催促语气推断。

## 稳定规格（.agent/specs/）

`.agent/specs/` 回答“项目今天应该成立什么”，`.agent/changes/WORK-*/` 回答“这次要改什么、怎么证明”。每个有意义的领域或契约一个文件（如 `architecture.md`、`auth.md`）；小项目一个 `project.md`，甚至没有也可以。不要因为目录存在就创建文件。

写多个工作项都会依赖的事实：外部可观察行为、公共接口与兼容规则、组件边界、数据不变量、安全约束、迁移规则。不要写临时头脑风暴、未批准提案、任务勾选、聊天记录、生成的 Git 历史、凭据或无依据的猜测。

起草变更前先读受影响规格；交付改变了稳定契约时，按已验证的结果更新规格，并保留变更文档作为理由和证据。不要为了让失败或未授权的变更看起来合规而提前改规格；如果实施发现规格或已批准需求是错的，把最早受影响的工件退回 `draft` 并重新取得批准。

权威顺序：已批准需求定本次范围，已批准设计和任务定实施路径，稳定规格定跨变更的当前契约，源码和可执行测试展示实际行为，Git 历史展示何时改变。冲突是漂移的证据：报告它并指出该修哪个工件，不要挑一个能让当前代码看起来正确的文档。

归档后工作项目录会变成 `changes/archive/YYYY-MM-DD-<名称>/`，旧路径引用失效：更新 `.agent/INDEX.md`、`specs/`、`rules/always.md`、`notes/` 和其他工作项里的活引用。`$lifecycle validate` 把这些报为警告（`--strict` 下视为失败）。

## 决策说明（.agent/notes/）

`.agent/notes/` 只收录从代码、工件和 Git 历史推不出来的理由：当初为什么这样定、放弃了什么、改它会影响什么。它不批准任何门槛；与已批准工件或真实源码冲突时，以后者为准并修正说明。

值得写：一个决定否决了看起来更简单的做法、字段或规则的语义容易被误读、能力被明确划到范围外、实现看起来绕但是某个约束逼出来的、为兼容旧数据或外部限制做了妥协。不写：格式化/命名/依赖补丁等机械改动、看代码和提交就能明白的单次实现细节、能从 Git 提交或已批准工件直接读到的账、流水账式开发日志。

一个决策一个文件，放在 `.agent/notes/`，用能读出主题的小写短横线名称（如 `api-time-format.md`）；文件名就是引用键，不另建编号表或索引。每篇按需使用这些小节：背景、问题、备选方案、决策与理由、代价和后果、什么情况下该重审。备选方案先写它最强的一面，再说明为什么没选，只写“不够好”会让后来的人重复提出；每个决定都要写放弃了什么、新增了什么负担。结论被取代时新建一篇，并在旧文件末尾追加 `- 替代：<新文件路径>`，不要就地改写已被取代的结论。

## 探索、实施与漂移

讨论中可以比较方案和修正假设；实施前锁定目标、边界和验收。实施中出现新的目标、接口、数据、安全、部署或架构要求时，先停下确认并使下游失效；仅内部路径、符号或命令变化且不改变范围时记录后继续。

## 跨对话接力

用户只需提供项目和编号：

```text
$project-lifecycle 在当前项目继续 WORK-003，先恢复规范和状态，再按当前阶段执行。
```

收到后必须重新执行本文件的固定顺序，把编号当定位键而非审批；多个活动项要求用户选择。任务已批准、项目事实已配置、硬依赖完成且无漂移时可直接实施，否则停在最早缺失门槛并说明原因。编号不存在时报告可用工作项，不得臆造。

状态输出在有助于接力或暴露阻塞时使用：

```text
当前：<中文工作项名称>（<WORK编号>）· <阶段> · <状态>
本次：<已完成的动作>
下一步：<下一动作或等待的确认>
接力：$project-lifecycle 继续 <WORK编号>，先恢复规范和状态，再按当前阶段执行。
```

没有持久化工作项的早期讨论不输出接力句，也不要每轮复述完整协议。

上下文压缩只影响对话历史，不改变项目工件。恢复时以 `.agent/changes/<WORK-*>/requirements.md` 的目标、验收标准和约束为任务事实源，以 `read_paths` 为读取清单；但工作项 `state` 是工件投影，不是源码实时扫描结果。`state_evidence.code_sync` 只有在 `testing/report.md` 声明 `verified_commit`，且该提交之后只有 `.agent/` 工件变化、当前工作区干净时才为 `verified`；这样报告本身可以在代码提交之后再提交，不会产生自引用哈希问题。缺少锚点为 `unknown`，锚点之后出现源码改动或工作区变化为 `stale`，格式错误为 `invalid`。只要不是 `verified`，`requires_reconciliation` 就为 true，不能替用户宣布源码与 Markdown 已同步。目标或验收标准缺失时先报告警告并补齐工件，不从摘要或模型记忆推断。

核心工作项 Markdown 还会做体积软检查：单文件超过 20,000 bytes、总量超过 80,000 bytes 或核心文件超过 6 个时只产生警告，不自动删除或压缩内容；恢复时按当前阶段读取，详细日志放入测试证据文件。

## 多对话并发与 Git 隔离

本 Skill 解决的是“换对话后恢复正确事实”和“多个活动工作项不串线”，不提供同一工作树的文件锁、实时协作编辑或自动合并。多个对话同时打开同一目录、同一分支并修改同一文件时，仍可能互相覆盖、产生冲突或把 Git 改动归到错误的工作项。

### 开始实施前询问 Worktree（仅在工作区不干净时）

`resume --json` 的 `worktree.decision` 有三种值，按它执行，不要自己另判：

| 值 | 含义 | 动作 |
| --- | --- | --- |
| `active` | 已在独立 worktree 内 | 不询问，直接实施 |
| `proceed` | 工作区干净 | 不询问，直接在当前目录实施并遵守单写入方约定 |
| `ask_user` | 工作区有未提交改动 | 问一次，见下 |

**只在 `ask_user` 时打断用户**。触发点仍是用户第一次要求实施某个 `WORK-*`，且即将修改源码、测试、配置或工件；只读调查、读文档、代码审查不触发。

```text
工作区有未提交改动。要不要为 WORK-003 开一个独立的 Git worktree？
- 开：在新分支 work/WORK-003 上工作，目录 ..\<项目>-WORK-003，不碰当前目录的改动
- 不开：直接在当前目录工作，同一时刻只允许一个写入对话
```

用户同意就在项目根执行：

```powershell
git worktree add "..\<项目>-WORK-003" -b "work/WORK-003"
```

用户拒绝或环境不支持（非 Git 仓库、已有目录冲突）就在当前目录工作，改为遵守“同一目录同一时刻只允许一个写入对话”，并在交接前用 `git status` 确认改动归属。

**问之前先核对三件事**，任一不满足就说明原因、不要硬开：

- 当前目录是 Git 仓库，且 `git status` 里没有属于其他工作项或来源不明的改动；
- 目标分支 `work/WORK-003` 和目录都不存在（`git worktree list` 已登记过的直接复用并告知路径）；
- **该工作项的 `.agent/changes/WORK-003-*/` 已提交**。新 worktree 只检出已提交内容，未提交的需求和任务文件不会出现在里面；没提交就先提交这些工件（只提交当前工作项归属的文件），或明确告知用户在旧目录继续。

**只问一次**：同一个工作项问过一次就不再重复；用户已在 worktree 内工作、或本会话明确答复过“不开”，都按已决处理。每个对话只负责一个 `WORK-*` 和一个 Worktree；完成后在自己的目录运行 `status`、`validate` 和测试，再由一个明确的整合对话审查差异并合并。

决定要写进事实源：创建成功后把分支、worktree 路径和创建时间写进当前工作项的 `design.md`（或 `.agent/notes/` 下的交接记录），这样换会话时能知道工作在哪个目录，而不是靠记忆。

`resume --json` 会带一个 `worktree` 字段，`decision` 只有两种值：`active`（已在链接 worktree 内，不要再问）和 `ask_user`（在主工作树里，改代码前问一次）。它只在当前阶段是 `implementation` 时出现；需求讨论、方案设计阶段不会提示。判定依据是 `git rev-parse --git-dir` 与 `--git-common-dir` 是否相同，不依赖目录名。

## 工作项标识、关系与批准

每个受管理需求有两个标识：`work_id`（如 `WORK-003`，稳定、不复用，用于关系和查询）和 `work`（用户可读的中文名，贯穿讨论、设计、实现和验收）。新需求首次讨论时先提出结果导向的中文名，只有存在两个实质不同的解释时才询问；编号用 `$lifecycle status <项目> --json` 返回的 `next_work_id`，不要从可见活动列表猜。随后立即创建 `.agent/changes/WORK-003-用户登录/requirements.md` 并写入用户原始目标和当前问题。目录名不能含保留字符、尾部空格/句点，也不要用“新需求”这类泛名；已持久化的工作项不静默改名。

工件 frontmatter 至少含：

```yaml
---
work_id: WORK-003
work: 用户登录
artifact: requirements | proposal | design | tasks | test-plan | test-report
status: draft | approved | stale
depends_on: [WORK-001]
related_to: [WORK-002]
updated: YYYY-MM-DD
---
```

`depends_on` 与 `related_to` 只写在 `requirements.md`，并引用 `WORK-*` 而不是名称或路径：

| 类型 | 含义 | 流程影响 |
| --- | --- | --- |
| `depends_on` | 没有对方的结果就不能正确实现或验收 | 实现前硬阻塞；未完成时只能讨论和设计 |
| `related_to` | 共享行为、契约、模块、数据或决策，但可独立交付 | 不阻塞；跨阶段前检查影响 |

同一结果或不能独立批准/验收的工作应合并，不用依赖代替；只有一个必须等待另一个的具体结果时才用 `depends_on`；可独立交付但共享行为或所有权时用 `related_to`；只有文件重叠而没有共享行为或决策时不建立关系。无法独立验收的工作也不能用依赖环代替：合并工作，或抽出共同前置工作项。

批准、实现或验证有关系的工作项前，比较共享需求、规格、接口、数据、安全约束、路径和验收。当前变更影响对方依赖的事实时，把对方最早受影响工件退回 `draft`、下游标为 `stale`；没有实质影响就在当前 proposal、design 或验证报告里记录结论，不因“有关联”而修改对方。长期契约放 `.agent/specs/`，工作项只引用不复制。

明确指向当前工件的“这版需求确认”“方案就这么定”“设计没问题，按它拆任务”“任务计划确认，开始做”可以批准；“继续”“开始做”“执行 `WORK-*`”只表达动作意图，除非同句明确批准。

### 签署

批准和签署是两件事：批准是门槛判断，签署是“谁在什么时候批的”这条审计事实。只有已经存在阶段门槛的工件需要签署，`lite` 短路径、`testing/plan.md` 和 `.agent/specs/` 不签（稳定规格的改动由工作项的需求和设计授权）。

| 工件 | 签署字段 | 签署人 |
| --- | --- | --- |
| `requirements.md` | `approved_by`、`approved_at`、`approver_role` | 需求方或业务负责人 |
| `proposal.md`、`design.md`、`tasks.md` | 同上 | 技术负责人 |
| `testing/report.md` | `accepted_by`、`accepted_at` | 验收人；只登记业务验收，不改报告状态 |

签署只走命令入口，时间戳由脚本盖：

```powershell
& $lifecycle approve "F:\我的项目" --work WORK-003 --artifact all --by "张三" --role "产品"
& $lifecycle approve "F:\我的项目" --work WORK-003 --artifact design --by "张三" --role "技术"
& $lifecycle approve "F:\我的项目" --work WORK-003 --artifact test-report --by "李四"
```

`--artifact all` 一次签完工作项里已存在的 `requirements/proposal/design/tasks`。用户说的“这一版可以，继续”通常就是一个整版确认，不必为每个文件各跑一次。业务验收仍要单独 `--artifact test-report`，且报告必须已是 `passed`。

`approve` 只会把 `status` 置为 `approved`、写入签署字段；不运行测试、不提交 Git、不推送。

规则：

- `approved_by`、`approved_at`、`approver_role`、`accepted_by`、`accepted_at` 只能由 `approve` 写入。Agent 不得凭自己的判断填写这些字段——那等于让模型替用户签字。
- `--by` 省略时取 `.agent/rules/always.md` 的 `approver`；两者都没有时先问一次用户姓名。不得编造或默认填“用户”、Agent 自己的名字（`approver` 只能来自已确认的 `.agent/rules/always.md`）。
- 用户明确批准时，Agent 可以代跑 `approve` 并回显写入的姓名和时间；用户也可以自己运行同一条命令。用户没批准就不要跑。
- 报告登记业务验收要求 `testing/report.md` 已经是 `passed`；`partial`、`failed` 或 `stale` 的报告拒绝登记。
- 工件缺签署时，状态输出会给出警告并阻断自动恢复；`validate` 按警告报告（旧工件保留原样），`validate --strict` 视为失败。签署时间戳格式错误一律是错误。
- 已批准工件被实质修改后要回到 `draft` 并重新签署；旧签署记录不删，作为时间线保留。

## 现有项目与小改动

现有项目没有 `.agent/` 时先读规则和文档；用户要求持久追踪或高风险管理时，说明初始化只增加项目资料、不改源码，再运行初始化器。单文件、低风险、边界清楚的小修复走短路径；新项目、跨模块、公共接口、迁移、安全和架构调整使用完整工作项。

## 归档

完成沉淀之后，工作项默认还留在活动列表里，每次状态查询都要为它输出签署、依赖和警告。归档把它移进 `.agent/changes/archive/YYYY-MM-DD-<名称>/`，是保持活动列表可读的正常收尾动作，不是可选项：

```powershell
& $lifecycle archive "F:\我的项目"            # 归档全部"完成沉淀 + 已完成"的工作项
& $lifecycle archive "F:\我的项目" --work WORK-003 --json
```

`archive` 只移动目录、不改文件内容；阶段不是完成沉淀或状态不是已完成的工作项会被跳过。归档后运行 `validate` 检查指向旧路径的引用（`changes/<名>` 会变成 `changes/archive/<日期>-<名>`）。已归档工作项只用于查阅，不能自动恢复。

不要创建 `.agent/current.md`、`state.json` 或手工状态索引；状态必须来自项目工件和查询器。

## 变更历史与提交边界

- 变更历史以 Git 提交为准：每轮改动写清提交信息（能定位 `WORK-*` 或维护事项），不再维护按轮追加的项目历史文件。
- 实际改动完成后直接报告本轮结果；没有运行的验证写“未运行”，不能写成通过。
- 用户要求本地保存时，只提交当前工作项归属的文件；用户已有和未知改动保持原样。
- 不因“保存”“提交”“继续”推断远端授权；`git push`、远端分支、tag 和部署必须由用户明确要求。
