# 自然语言执行与跨对话接力协议

本文件是受管理工作项的标准执行协议：它定义自然语言触发、每轮动作和跨对话恢复；各阶段工件的写法仍由对应参考文件负责。

## 核心约定

- 用户用自然语言即可；低风险、边界清楚的孤立改动走短路径。
- `WORK-*` 是稳定定位键，不是代码命令，也不代表批准。
- `.agent/` 工件是事实源；聊天、时间戳和记忆不能代替状态。
- `.agent/INDEX.md` 只做模块/资料导航，`.agent/html/` 只放理解材料；外层 `PROJECT-INDEX.md` 只导航多仓库。
- 换会话、上下文压缩或用户说“继续”时，先恢复规范和状态；用户明确批准后才能跨阶段门槛。

## 用户如何触发

| 用户表达 | 当前动作 | 持久结果 |
| --- | --- | --- |
| “我有个想法”“想加功能” | 讨论范围、约束和验收 | 稳定后创建 `requirements.md` |
| “把需求问透”“先访谈再出 PRD/Task” | 进入 `requirements-interview.md` 的逐轮模式 | 持续更新需求，最终确认后进入流程 |
| “把刚才内容整理成需求” | 综合上下文和仓库事实，只问真实缺口 | 更新 `requirements.md` |
| “这版需求确认” | 明确批准需求 | `requirements.md` 为 `approved` |
| “给个方案”“需求确认了，继续” | 推荐方案并说明取舍 | `proposal.md` |
| “方案可以，做设计” | 批准方案并完成设计 | `design.md` |
| “设计没问题，拆任务” | 批准设计并拆执行计划 | `tasks.md` |
| “按计划开始做”“实施 WORK-003” | 恢复状态，门槛满足后实现 | 源码、测试和任务状态 |
| “测试一下”“验收 WORK-003” | 按验收标准做真实验证 | 测试计划和报告 |
| “当前状态”“查询 WORK-003” | 从工件推导阶段、关系和下一步 | 默认不修改工件 |

显式写 `$project-lifecycle` 总能请求本 Skill；孤立小修复不必强行创建工作项。

## 每轮固定顺序

1. **确定项目**：多仓库先读外层 `PROJECT-INDEX.md` 和项目映射，再读目标项目的 `AGENTS.override.md`、`AGENTS.md` 和说明；需要定位模块时再读项目 `.agent/INDEX.md`。
2. **恢复规范**：读 `.agent/rules/always.md`。文件缺失、草案、无效或冲突时先查仓库并提出草案；可以继续只读讨论和不依赖未知规则的设计/验证，但实现、部署、迁移和数据变更必须等待确认。
3. **查询状态**：从 Skill 安装目录运行：

   ```sh
   python -X utf8 scripts/project_status.py <project-root> --json
   python -X utf8 scripts/project_status.py <project-root> --resume --json
   ```

   `--resume` 返回 `auto_resume`、`ask_user` 或 `out_of_scope`，并给出阶段、阻塞、建议读取路径和接力提示。下游按 `schema_version` 和字段读取，不解析中文文本。
4. **定位和加载依据**：按用户点名的编号、中文名、内容唯一匹配、唯一活动项的顺序选择；先读需求，再按阶段读取已批准工件、规格、记忆和共享资料。
5. **检查门槛并执行一个动作**：核对规范、批准、硬依赖、关联影响和工件一致性；然后讨论、写当前工件、改代码、验证，或停在真实确认点。
6. **同步事实**：只按实际结果更新工件和任务状态；需要接力或暴露阻塞时再输出状态。

发布或交接前可运行：

```sh
python -X utf8 scripts/project_validate.py <project-root> --strict --json
```

它检查结构、标识符、来源引用、测试证据和 Git 归因；`--strict` 将兼容性警告视为失败。

## 工作区归因与多仓库边界

恢复前必须查看状态输出中的 Git 概览。存在 staged、unstaged 或 untracked 改动时，在当前工作项下创建/更新 `workspace.md`，记录 `base_commit` 和每条路径的 `current_work`、`user_existing` 或 `unknown` 归属；所有路径已归类、基准未变且没有未知归属后，恢复探针才可自动继续。不得因为聊天或任务文件说“完成”就覆盖、清理或提交未授权改动。

```markdown
---
base_commit: <当前基准 commit>
---

## 工作区归因

| 路径 | 归属 | 说明 |
| --- | --- | --- |
| src/login.ts | current_work | TASK-001 的实现 |
| README.md | user_existing | 用户原有未提交修改 |
```

外层 `.agent/` 不承载项目状态；进入开发、验证或恢复 `WORK-*` 时必须切换到真实项目目录。初始化器创建项目内 `.agent/INDEX.md` 和 `.agent/html/`：索引登记源码、配置、测试、规格、工作项和理解材料的位置，不记录阶段或任务状态；HTML 只用于解释架构、流程、状态机、数据流或交互，不是运行时依赖或验收证据。

## 阶段门槛

`requirements.md` 的 `workflow: compact` 允许省略 proposal/design，只保留批准需求、任务计划和验证报告；不得用它绕过安全、迁移、公共接口或架构所需的设计。

| 当前事实 | 当前阶段 | 允许的动作 |
| --- | --- | --- |
| 需求不存在或为 `draft` | 需求讨论 | 澄清、修订并等待确认 |
| 需求已批准，提案缺失/`draft`/`stale` | 方案选择 | 创建或修订提案并等待确认 |
| 提案已批准，设计缺失/`draft`/`stale` | 详细设计 | 结合真实代码完成设计 |
| 设计已批准，任务缺失/`draft`/`stale` | 实施计划 | 拆可独立验证的纵向切片并等待确认 |
| 任务已批准且有未完成任务 | 开发实现 | 无硬依赖和规范阻塞时改代码并同步任务 |
| 任务完成但没有通过验证报告 | 测试验收 | 记录证据、缺口和风险 |
| 上游一致、任务完成、验证通过 | 完成沉淀 | 核对规格、记忆并可选归档 |

如果后期工件存在但更早阶段缺失、未批准或失效，回到最早受影响阶段。用户可以明确合并或豁免门槛，但决定必须写入受影响工件，不能从催促语气推断。

## 探索、实施与漂移

讨论中可以比较方案和修正假设；实施前锁定目标、边界和验收。实施中出现新的目标、接口、数据、安全、部署或架构要求时，先停下确认并使下游失效；仅内部路径、符号或命令变化且不改变范围时记录后继续。

## 跨对话接力

用户只需提供项目和编号：

```text
$project-lifecycle 在当前项目继续 WORK-003，先恢复规范和状态，再按当前阶段执行。
```

收到后必须重新执行本文件的固定顺序，把编号当定位键而非审批；多个活动项要求用户选择。任务已批准、项目事实已配置、硬依赖完成、工作区已归因且无漂移时可直接实施，否则停在最早缺失门槛并说明原因。编号不存在时报告可用工作项，不得臆造。

状态输出在有助于接力或暴露阻塞时使用：

```text
当前：<中文工作项名称>（<WORK编号>）· <阶段> · <状态>
本次：<已完成的动作>
下一步：<下一动作或等待的确认>
接力：$project-lifecycle 继续 <WORK编号>，先恢复规范和状态，再按当前阶段执行。
```

没有持久化工作项的早期讨论不输出接力句，也不要每轮复述完整协议。

## 工作项选择、关系与批准

硬依赖 `depends_on` 未完成时可以讨论和设计，但不能实现或验收；`related_to` 不阻塞，跨阶段前检查共享接口、数据、模块和验收。无法独立批准/验收的需求应合并，不能用循环依赖代替。

明确指向当前工件的“这版需求确认”“方案就这么定”“设计没问题，按它拆任务”“任务计划确认，开始做”可以批准；“继续”“开始做”“执行 `WORK-*`”只表达动作意图，除非同句明确批准。

## 现有项目与小改动

现有项目没有 `.agent/` 时先读规则和文档；用户要求持久追踪或高风险管理时，说明初始化只增加项目资料、不改源码，再运行初始化器。单文件、低风险、边界清楚的小修复走短路径；新项目、跨模块、公共接口、迁移、安全和架构调整使用完整工作项。

不要创建 `.agent/current.md`、`state.json` 或手工状态索引；状态必须来自项目工件和查询器。
