# 决策说明（Agent Notes）

当用户询问“当初为什么这么做”、需要记录跨工作项仍有效的决策理由，或准备修改一条既有决策时读取本参考。

## 目的与边界

`.agent/notes/` 回答“当初为什么这样决定、放弃了什么、改它会影响什么”。它只收录从代码、工件和 Git 历史推不出来的内容。

| 问题 | 去哪里 |
| --- | --- |
| 项目现在应该怎样工作 | `.agent/specs/` |
| 这次要改什么、怎么证明改对 | `.agent/changes/WORK-*/` |
| 哪天改了什么、依据和验证 | `.agent/history/updates.md` |
| 跨任务仍要记住的事实 | `.agent/memory.md` |
| 当初为什么这么定、备选是什么、改它会怎样 | `.agent/notes/` |
| 提交身份、作者、时间和可回滚事实 | Git |

决策说明不复制代码能直接读出的事实，否则就是又一份需要同步的副本。它不批准任何门槛、不扩大范围；与已批准工件或真实源码冲突时，以后者为准并修正说明。

## 什么时候写一篇

- 一个决定否决了看起来更简单的做法，后来的人可能想再试一次；
- 一个字段或规则的语义容易被误读，改掉它会让下游失效；
- 一个能力被明确划到范围外，需要留下理由，避免反复被提起；
- 一处实现看起来啰嗦或绕，其实是某个约束逼出来的；
- 为一个不可见的约束做了妥协，例如兼容旧数据、外部系统限制、性能或合规要求。

## 什么时候不写

- 机械性改动：格式化、纯命名或标记调整、行为保持的依赖补丁、常规 CRUD；
- 单次性实现细节，看代码和提交就能明白；
- 能从 `.agent/history/updates.md` 或已批准工件直接读到的账；
- 流水账式的开发日志。

过度记录和记录不足是同一个错误的两种样子：两者都会让后来的人找不到真正有用的那一条。

## 写作结构

每篇按同一结构，只写与本次决策相关的部分：

````markdown
# <决策主题>

## 背景
## 问题
## 备选方案
## 决策与理由
## 代价和后果
## 什么情况下该重审
````

- **备选方案**：每个方案先写出它最强的一面，再说明为什么没选。只写“不够好”而不写它成立的理由，等于立了一个稻草人，后来的人会重复提出它。
- **代价和后果**：每个决定都要写它放弃了什么、新增了什么负担。没有代价的决定是挑选过的。
- **什么情况下该重审**：写明失效条件，让决策将来可以被重新讨论，而不是变成不可质疑的教条。

## 文件与命名

一个决策一个文件，放在 `.agent/notes/`，用能读出主题的小写短横线名称，例如 `.agent/notes/api-time-format.md`。文件名就是它的引用键：不要另建编号表或索引，那会变成第二份需要同步的副本。同一主题的局部补充写在原文件里，不要为此新建一篇。

## 失效与替代

- 证据可能失效时复核该篇，并把结论标记为过时，不要静默保留。
- 结论被取代时新建一篇，并在旧文件末尾追加一行 `- 替代：<新文件路径>`，说明它为什么过期。
- 不要就地改写已被取代的结论：保留它，让后来的人看到演进的路径。

## 与长期记忆的关系

`.agent/memory.md` 的“依据”字段可以指向这里的文件。记忆保存一句可检索的结论，完整论证放决策说明；记忆条目不承担论证，决策说明也不承担跨任务检索。
