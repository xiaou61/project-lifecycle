# Project Lifecycle

把项目工件作为长期事实源，把聊天作为当前交互。只有需要跨会话追踪、多人协作或有明显风险的工作才使用完整工作项。

## 运行时底线

- 低风险、边界清楚的孤立改动：直接确认目标、修改代码并验证，不创建完整工作项。
- 重要工作开始或恢复时：读取适用的 `AGENTS.override.md`、`AGENTS.md`、`.agent/rules/always.md`，再用 `project_status.py --json` 定位项目和工作项。
- 上下文压缩或换会话后，按同样顺序重新加载；不要把聊天记忆当作批准、规则或当前状态。
- 用户明确批准后才能跨过需求、方案、设计或任务门槛；“继续”只表示继续已获授权的动作。
- 只按已确认范围实施。目标、验收标准、公共行为、接口、数据、安全或架构发生实质变化时，停下，退回最早受影响的工件，并使下游工件失效。
- 运行相关测试或检查，真实记录通过、失败、未运行和人工缺口；不能把代码阅读当成测试证据。
- 不覆盖用户资料，不伪造批准、状态、测试结果或长期记忆。

## 按风险选流程

| 工作 | 默认动作 |
| --- | --- |
| 小修复、单文件、边界明确 | 聊天确认 -> 修改 -> 窄验证 |
| 需要跨会话追踪的普通功能 | 创建 `WORK-*`，在 `requirements.md` 标记 `workflow: compact`，保留需求、计划和验证资料 |
| 新项目、跨模块、公共接口、数据、安全、迁移、架构 | 使用完整的需求 -> 方案 -> 设计 -> 任务 -> 实现 -> 验证流程 |

不要为了形式创建空白工件。用户要求记录时可以把合并阶段和豁免写入当前工件；不能默默跳过门槛。

## 受管理工作的一轮动作

1. 确认项目根目录和适用规则。
2. 查询工作项状态、任务、依赖和阻塞。
3. 只加载当前阶段需要的工件、稳定规格和匹配记忆。
4. 继续讨论、等待确认、修改代码或运行验证中的一个明确动作。
5. 按实际结果同步任务、测试报告、规格和长期记忆。
6. 用最短的文字说明当前状态和下一步；只有跨会话接力有价值时才给出接力句。

## 参考资料

按需读取：`references/workflow.md`（详细路由与恢复）、`requirements.md`（需求）、`proposal.md`（方案）、`design.md`（设计）、`tasks.md`（任务）、`testing.md`（验证）、`memory.md`（长期记忆）、`specs.md`（稳定规格）。

## 边界

本 Skill 不规定一个 `WORK-*` 对应一个 Git 分支，不自动提交 Git，不选择模型思考等级，也不提供自动语义证明。Git、源码和可执行测试仍是各自领域的事实源。
