# QA：30 个使用问题

这页把常见的“我该怎么用”直接对应到 `project-lifecycle` 的入口、工件和边界。示例默认使用 Windows PowerShell；`$lifecycle` 指向已安装 Skill 的统一命令入口：

```powershell
$lifecycle = "$env:USERPROFILE\.codex\skills\project-lifecycle\scripts\project-lifecycle.ps1"
```

## 认识这套 Skill

### 1. `project-lifecycle` 到底解决什么问题？

它把一次开发工作中的需求、决定、任务、依赖、测试证据和阻塞写入项目的 `.agent/`，让 Agent 在换对话、上下文压缩或多人接力后重新读取事实，而不是只凭记忆猜进度。它还按风险选择路径：小修复走 `lite`，普通功能使用 `managed`（`compact`），跨模块、公共接口、数据、安全、部署或架构变更使用 `strict`（`full`）。

它不是项目管理看板、实时协作编辑器或 CI/CD 平台。源码和测试仍在项目原有目录，Skill 只增加资料工作区和只读状态/校验入口。

### 2. 什么任务应该使用它？

需要跨会话继续、多人协作、明确审批、依赖关系、验收证据或明显风险的工作应该使用。比如新增登录、改公共接口、数据库迁移、部署配置、跨模块重构，以及需要几天完成的功能。

一个文件里改一处拼写、边界明确且不需要后续接力的小修复，可以确认目标后直接改并做窄验证，不必为了形式创建 `WORK-*`。是否创建工作项取决于恢复和审计需要，不取决于文件数量本身。

### 3. 如何安装？

在 Codex 中让 `$skill-installer` 从仓库的 Skill 目录安装：

```text
使用 $skill-installer 从 https://github.com/xiaou61/project-lifecycle/tree/main/skills/project-lifecycle 安装 project-lifecycle。
```

安装后由 Codex 根据 Skill 描述自动触发，也可以显式写 `$project-lifecycle`。普通用户不需要把仓库里的 Python 脚本复制到目标项目，更不要从目标项目的 `.agent/scripts/` 猜路径。

### 4. 初始化会改我的源码吗？

不会。初始化器只在目标项目增加入口模板和 `.agent/` 资料目录，保留已有源码、测试、`AGENTS.md` 和 Git 历史；它不会创建空白工作项、移动旧目录或猜测项目规则。

```powershell
& $lifecycle init "F:\我的项目"
```

初始化是幂等的，可以重复执行。第一次初始化后仍要由用户确认项目长期规则，Skill 才能把规则视为可执行约束。

### 5. 为什么还要确认 `.agent/rules/always.md`？

它保存跨多个工作项都有效的项目事实，例如技术栈、检查命令、部署目录和安全边界。初始化器不能替用户猜这些内容；未确认时可以讨论、设计和做不依赖未知规则的只读验证，但实现、部署、迁移和数据变更会停下。

这条规则防止一次聊天中的临时偏好被误当成项目永久规范。确认后规则必须有明确的 `status: active` 和 `configured: true`，换对话时仍会重新读取。

### 6. 我只想用自然语言，可以吗？

可以。推荐这样推进：

```text
我想增加用户登录，先聊聊这个需求。
这版需求确认，继续给方案。
方案可以，结合当前代码做设计。
设计没问题，按它拆任务。
任务计划确认，开始做。
测试一下，告诉我哪些验收项过了。
```

每句话对应一个阶段动作。`继续`、`开始做` 和 `执行 WORK-*` 表示动作意图，不自动等于需求、方案、设计或任务计划批准；需要跨门槛时必须有明确确认。

## 需求与工作项

### 7. `WORK-*` 是什么？为什么还要中文名称？

`WORK-*` 是稳定的机器定位键，例如 `WORK-003`，用于关系、命令查询和跨对话接力；中文名称是给人阅读和消歧的，例如“用户登录”。编号不能复用，中文名称在同一工作项生命周期中保持不变。

状态查询会返回下一个可用编号，Agent 不应根据目录顺序或聊天猜编号。工作项目录通常是 `.agent/changes/WORK-003-用户登录/`。

### 8. 什么时候需要先把需求问透？

当目标用户、范围、异常行为、数据归属、外部接口、安全边界或验收方式会改变交付结果时，使用需求深挖访谈。它是可选增强，不会把每个小修复变成问卷。

一次只问一个真正影响范围的问题；已能从代码、配置或正式资料查到的事实由 Agent 先调查，不伪装成用户问题。访谈结束后仍需用户确认最终摘要，才能把 `requirements.md` 标为 `approved`。

### 9. 需求、PRD 和 Task 分别放在哪里？

本 Skill 把 `requirements.md` 作为项目内 PRD，保存目标、范围、验收标准、用户决定和来源覆盖；`tasks.md` 保存可执行的 `TASK-*` 纵向切片。`full` 流程中还会有 `proposal.md` 和 `design.md`，分别记录方案取舍与技术设计。

它们位于当前工作项目录，而不是仓库根目录：

```text
.agent/changes/WORK-003-用户登录/
  requirements.md
  proposal.md
  design.md
  tasks.md
  testing/plan.md
  testing/report.md
```

不要另建一份同内容的 `prd.md` 造成两个事实源。

### 10. `lite`、`managed` 和 `strict` 怎么选？

`lite` 适合单文件、低风险、边界明确的小修复；`managed` 适合需要跨会话追踪的普通功能，对应 `workflow: compact`；`strict` 用于跨模块、公共接口、数据、迁移、安全、部署或架构工作，对应 `workflow: full`，需要按“需求 -> 方案 -> 设计 -> 任务 -> 实现 -> 验证”逐阶段批准。

`managed` 不是跳过安全或迁移设计的快捷键。只要公共行为或数据边界发生实质变化，就应升级到 `strict`。模式不是测试数量开关，严格模式也只执行最窄可信检查。

### 11. 依赖关系会怎样影响执行？

`depends_on` 表示没有另一个工作项的结果就不能正确实现或验收，是硬阻塞；`related_to` 表示共享模块、契约或决策但可以独立交付，不阻塞实现。两者都写在 `requirements.md`，引用 `WORK-*` 而不是文件路径或中文名。

状态查询会显示正向依赖、反向被依赖和关联项；硬依赖未完成时，当前工作项不能进入实现。依赖环或自依赖会直接阻断并要求拆分或合并。

## 多对话与并发修改

### 12. 我换一个对话后，能继续原来的工作吗？

可以。新对话先执行：

```powershell
& $lifecycle resume "F:\我的项目" --json
```

结果会给出 `resume.mode`、当前工作项、阶段、阻塞原因、建议读取路径和可复制的接力句。新对话按这些路径重新读取规则和工件，再继续当前阶段；聊天记录和模型记忆不作为唯一事实源。

### 13. 我有三四个对话同时做同一个项目，目前解决了吗？

只解决了一半。它已经能处理多个活动工作项的选择、跨对话恢复、Git 脏改动归因和依赖阻塞，避免新对话根据“最近聊天”误选工作项；但它没有文件锁、实时协作编辑或自动合并能力。

因此，同一目录、同一分支里让多个对话同时写同一个文件仍然可能互相覆盖、产生冲突或污染归因。这个边界必须按 Git 协作规则处理，不能把 `resume` 当成并发编辑器。

### 14. 三四个对话并行时，推荐怎样安排？

推荐“一项工作、一个分支、一个 Worktree、一个写入对话”。例如为 `WORK-003` 创建独立目录：

```powershell
git worktree add "..\我的项目-WORK-003" -b "work/WORK-003"
```

该对话只在新目录处理 `WORK-003`；其他对话使用不同工作项和不同 Worktree。各自完成后，在自己的目录运行测试、`status` 和 `validate`，由一个整合对话查看差异并合并。

只读调查、文档阅读和代码审查可以共享目录。会写源码、测试、配置或 `.agent/` 的对话必须先确认目录归属。

### 15. 如果不能使用 Git Worktree 怎么办？

采用人工写入排他：同一目录同一时刻只允许一个对话修改，其他对话只读或等待。切换前执行：

```powershell
& $lifecycle checkpoint "F:\我的项目" --json
```

若结果显示 `dirty`，先在当前工作项的 `workspace.md` 逐项标记 `current_work`、`user_existing` 或 `unknown`。看到未知改动时先让用户确认，不覆盖、不清理、不替别人提交。这个办法降低误操作概率，但仍不替代分支合并和冲突解决。

### 16. 多个活动工作项时，Skill 会替我选哪个？

不会。没有明确选择时，`resume` 返回 `ask_user`，列出候选项；不会按目录时间、Git 最近修改时间或最近对话猜测。你可以按编号或中文名称指定：

```powershell
& $lifecycle status "F:\我的项目" --work WORK-003
& $lifecycle resume "F:\我的项目" --work "用户登录"
```

也可以在对话中写“在当前项目继续 `WORK-003`，先恢复规范和状态”。编号只是定位，不会绕过审批门槛。

## 实现、验证与质量门槛

### 17. 为什么 Git 脏了不能直接继续？

未提交改动可能来自当前工作、用户正在做的另一项工作或未知来源。自动把所有文件归给当前 `WORK-*` 会让错误前提进入实现，自动清理则可能造成数据丢失。

恢复时检查 `git.status`、改动数量和归因状态；只有每条改动都写入 `workspace.md`、归属有效且 `base_commit` 对得上，才会把归因视为 `complete`。脏工作区本身不等于失败，但不能被默认为任务完成或验证通过。

### 18. `status`、`resume` 和 `validate` 有什么区别？

`status` 回答“项目现在到哪一步、有哪些工作项、下一步是什么”；`resume` 专门输出新对话需要的上下文、阻塞和接力提示；`validate` 检查工件结构、重复 ID、来源引用、测试证据和 Git 归因，适合发布或交接前。

```powershell
& $lifecycle status "F:\我的项目"
& $lifecycle resume "F:\我的项目" --json
& $lifecycle validate "F:\我的项目" --json
```

自动化应读取 JSON 的 `schema_version`、`resume.mode`、`errors` 和 `warnings` 等字段，不要解析中文输出的位置或标点。

### 19. 验收标准为什么要写成 `AC-*`？

`AC-*` 让需求、测试计划和验证报告可以逐项对应。例如 `AC-001` 是“登录成功”，测试报告必须写出命令、退出码、结果和证据位置。这样“测试通过”不再只是聊天中的一句话，而是可复查的证据链。

没有正式外部来源时不必强行创建来源覆盖表；使用 Issue、附件、PRD 或链接作为依据时，才为每条外部事实记录来源和锚点。

### 20. `testing/report.md` 写了 `passed` 就算完成了吗？

不算。`passed` 只表示报告中列出的检查证据通过，不等于用户业务验收、发布授权或线上验证。需要作为完成结算依据时，报告 frontmatter 增加 `evidence: required`，并以表格覆盖所有 `AC-*`：

```markdown
| 检查项 | 命令 | 退出码 | 结果 | 证据 |
| --- | --- | --- | --- | --- |
| AC-001 | `pytest tests/test_login.py -q` | 0 | passed | `testing/logs/login.txt` |
```

需求或实现发生实质变化后，旧报告应标成 `stale` 并重新验证。默认不会额外安排通用冒烟测试；只有用户、项目长期规则或已批准测试计划明确要求时才执行，并在报告中记录范围和证据。

### 21. 严格校验什么时候运行？

发布、交接或完成沉淀前运行：

```powershell
& $lifecycle validate "F:\我的项目" --strict --json
```

它会检查初始化状态、项目规则、工件 frontmatter、`REQ-*`/`AC-*`/`TASK-*` 重复、依赖和循环、来源覆盖、结构化测试证据、失效报告以及 Git 归因。普通状态查询用于推进工作，不应被当成发布检查替代品。

### 22. 发现需求变了，能不能继续沿用旧的 Task？

只有不改变目标、验收、公共行为、接口、数据、安全、部署或架构的内部路径调整可以记录后继续。出现实质变化时，回到最早受影响的工件，把下游 proposal、design、tasks 或报告标成 `stale`，重新批准后再实现。

这样做会多一次确认，但能避免“旧 PRD + 新实现 + 旧测试”拼成看似完整、实际不可追溯的结果。

## 历史、索引与理解材料

### 23. 每次修改怎么留下更新历史？

目标项目初始化后有 `.agent/history/updates.md`，每次实际改源码、测试、配置、Skill 规则、文档或工件都追加一条记录，至少写变更、决策、依据、验证、本地提交和远端推送边界。新记录标题精确到秒并带本地时区，例如 `2026-09-09 13:47:43 +0800`；旧的纯日期记录仍可正常读取。记录是追加式的，发现错误时追加更正，不覆盖旧事实。

查看最近记录：

```powershell
& $lifecycle updates "F:\我的项目" --tail 10
```

### 24. `record` 会自动提交或推送吗？

不会。它只追加结构化文本，不创建 Git commit，也不执行 `push`：

```powershell
& $lifecycle record "F:\我的项目" --work WORK-003 --title "修复登录超时" --type implementation `
  --change "调整会话超时处理" --decision "保留现有接口" `
  --basis ".agent/changes/WORK-003-用户登录/design.md" `
  --verification "pytest tests/test_login.py -q：通过"
```

本地提交、远端分支、tag、部署都需要单独的用户授权；更新记录里必须如实写“待用户授权/未提交”或“未执行”。

### 25. `checkpoint` 检查什么？

它是切换工作项或交接前的只读检查，主要确认 Git 工作区是否还有未提交改动：

```powershell
& $lifecycle checkpoint "F:\我的项目" --json
```

返回非零表示工作区仍需处理，不表示代码一定错误。它不会替你归因、提交或清理文件；先完成 `workspace.md`，再由用户决定是否创建本地 commit。

### 26. 总索引、项目 `.agent/INDEX.md` 和 Git 历史有什么区别？

教程站的[总索引](/reference/)是这个 Skill 仓库的维护地图，说明模块改哪里、改完到哪里看；目标项目的 `.agent/INDEX.md` 只导航源码、测试、规格、工作项和 HTML；Git 历史记录提交、作者、文件和可回滚事实。

三者都不是阶段状态数据库。阶段、批准、任务和验证仍以目标项目 `.agent/changes/` 中的工件和状态查询结果为准。

### 27. HTML 理解材料应该放在哪里？

项目理解型 HTML 只在用户明确同意生成某份材料后，放入目标项目的 `.agent/html/<主题>.html`，并在 `.agent/INDEX.md` 登记。它可以解释架构、流程、状态机或数据流，但不是运行时依赖，也不能替代源码、测试、批准或验证报告。

Skill 仓库的 `docs/` 是正式 VitePress 教程，`output/` 是交付产物；不要把某个目标项目的图误放进可复用 Skill 本体。

### 28. 可以把 HTML 当成系统真实状态吗？

不可以。生成 HTML 前要先读取真实源码、配置、测试和项目工件；如果图和事实冲突，标注冲突并以事实源为准。HTML 是解释和探索材料，适合帮助人理解，不参与状态推导、审批和验收。

## 发布与边界

### 29. Skill 会自动提交、推送或部署吗？

不会。默认只在本地修改和验证；本地 commit 是可恢复检查点，`git push`、创建远端分支、tag 和部署必须得到用户明确授权。用户明确要求发布时，也要先完成更新历史、归因、测试和发布前校验，再执行对应的 Git/部署流程。

这条边界把“代码已经改好”“已经形成本地检查点”“已经推到远端”“线上已经验证”分成四个可核对事实，避免把一个动作的成功误报成全部完成。

### 30. 它不能替我解决什么？

它不提供同一目录的并发锁、不自动合并分支、不运行数据库、不拦截所有 Agent 写入、不替代 CI/CD、线上监控或业务验收，也不会凭空补齐缺失的来源和测试证据。遇到这些需求时，使用 Git 分支/Worktree、项目现有测试和部署工具，并把外部结果记录回工作项。

最短可靠组合是：先用 `status/resume` 恢复事实，按工作项隔离写入，完成后用测试和 `validate` 证明，再用 `updates/record/checkpoint` 留下可追溯记录。需要进一步了解阶段门槛，可阅读[全流程教程](/guide/full-workflow)和[边界与常见问题](/reference/boundaries)。
