# 全流程教程

完整工作项把一次高风险或跨模块变更拆成可批准、可恢复、可验证的阶段。每个阶段只完成自己负责的事情，后续阶段不能反过来替前面阶段批准。

## 先选风险模式

开始时先判断一次：

| 模式 | 适用情况 | 做法 |
| --- | --- | --- |
| `lite` | 单文件、低风险、边界明确 | 直接修改并做最窄验证，不创建完整 `WORK-*` |
| `managed` | 普通多步骤功能，需要跨对话追踪 | 创建 `WORK-*`，在 `requirements.md` 写 `workflow: compact` |
| `strict` | 公共接口、数据、迁移、安全、部署、架构或跨模块变更 | 创建 `WORK-*`，走 `workflow: full` 全阶段 |

模式不是测试数量开关。风险升高时只能从 `lite` 升级到 `managed` 或 `strict`；不能用低模式绕过设计、安全和数据门槛。`strict` 仍按验收矩阵执行最窄可信验证。

## 阶段顺序

| 阶段 | 主要工件 | 进入条件 | 产出 |
| --- | --- | --- | --- |
| 需求讨论 | `requirements.md` | 目标、范围和验收仍在收敛 | 可观察的需求和 `REQ-*`、`AC-*` |
| 方案选择 | `proposal.md` | 需求已明确批准 | 真实取舍和推荐方案 |
| 详细设计 | `design.md` | 方案已明确批准 | 组件、接口、数据流和失败行为 |
| 实施计划 | `tasks.md` | 设计已明确批准 | 可执行、可验证的任务 |
| 开发实现 | 源码、测试、任务状态 | 任务计划已批准且没有阻塞 | 代码和实际执行记录 |
| 测试验收 | `testing/plan.md`、`testing/report.md` | 实施任务全部完成 | 证据、缺口和剩余风险 |
| 完成沉淀 | `specs/`、`memory.md`、归档 | 验证通过且事实一致 | 可复用的当前事实 |

## 需求阶段

先检查仓库能直接回答的问题，再问会改变范围、用户行为、数据归属、接口、安全或验收的问题。把“已确认事实”“用户决定”“实现选择”和“待确认问题”分开写；只有最后一类会阻断需求批准。

如果用户明确要求“把需求问透”或“先访谈再生成 PRD/Task”，先进入[需求深挖访谈](/guide/requirements-interview)：一次只问一个关键问题，持续更新 `requirements.md`，完成最终确认后再按 `compact` 或 `full` 继续。

需求批准前，`requirements.md` 保持：

```yaml
status: draft
```

用户明确说“这版需求确认”后，解决或记录影响范围的待确认问题，再改为 `approved`。不要把“继续”“开始做”当成需求批准。

## 方案、设计和任务

方案阶段比较实现路径，说明成本、风险和真正的取舍。设计阶段结合真实代码，明确公共行为、接口、数据、失败和回滚边界。任务阶段把设计拆成能单独执行、能单独验证的步骤。

任务拆分优先采用纵向切片：每个任务覆盖本次变更需要的必要层，完成后能独立演示或验证用户可见行为；每个任务只声明真正会阻塞它的任务。一次性机械重构才使用“扩展、迁移、收缩”的顺序。

每个阶段都需要用户明确批准后才能跨过去。若用户修改了目标、公共行为、接口、数据、安全、部署或架构，回到最早受影响的工件，并把下游工件标记为 `stale`。

## 实现阶段

开始实施前确认：

- `tasks.md` 已批准；
- 项目常驻规则已确认；
- `depends_on` 中的硬依赖已完成；
- 当前需求没有漂移；
- Git 工作区已有改动已经完成归因。

任务状态只按真实执行结果更新。测试通过不等于任务自动完成，任务完成也不等于业务验收完成。

## 每轮更新与本地检查点

每次实际修改源码、测试、配置、文档或项目工件后，在 `.agent/history/updates.md` 追加一条记录，至少说明：

- 改了什么，以及涉及哪些工作项或维护事项；
- 采用了什么决策，放弃了什么方案，依据在哪里；
- 实际运行了哪些验证，哪些没有运行；
- 本地提交哈希，或“待用户授权/未提交”的原因；
- 远端推送状态。默认不推送，只有用户明确要求时才执行。

`.agent/history/updates.md` 是可读时间线；Git 是提交和回滚事实源，工作项工件仍保存完整需求、任务和验证。切换到下一个独立工作项或进入完成沉淀前，必须先完成历史记录，并确认当前改动已经本地提交或明确停在本地提交授权门槛。

## 验证和完成

测试计划应把验收标准映射到实际检查、预期结果和证据位置。报告要区分：

- `passed`：检查证据通过；
- `partial`：部分通过，仍有缺口；
- `failed`：检查失败；
- `stale`：上游需求或实现已变化，需要重验。

需要用于完成结算时，在报告 frontmatter 写 `evidence: required`，并用表格记录每个 `AC-*` 的命令、退出码、结果和证据路径。

只有上游工件一致、任务完成、验证报告通过，工作项才进入完成沉淀。`passed` 不等于用户已经验收，也不自动授权发布。

发布或交接前可运行 `project-lifecycle.ps1 validate`，检查重复标识符、来源引用、结构化测试证据和 Git 归因。

## 普通功能的 compact 流程

普通功能可以在 `requirements.md` 的 frontmatter 中明确：

```yaml
workflow: compact
```

它保留已批准需求、简短任务计划和验证资料，省略独立的方案和设计工件。不要用 `compact` 绕过安全、迁移、公共接口或架构工作所需的设计。

`compact` 是 `managed` 模式写入工件时使用的兼容字段；旧工件没有 `mode` 时，状态查询会把 `compact` 推导为 `managed`、把 `full` 推导为 `strict`。
